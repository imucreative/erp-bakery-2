# 1. Executive Summary

This document defines the **single source of truth** for Role-Based Access Control (RBAC) across the Bakery ERP system.

Its objectives are:

- Standardize permission naming.
- Standardize permission metadata using Business Domain -> Module -> Action.
- Define default permissions for each role.
- Eliminate inconsistencies introduced during Sprint 1.
- Serve as the reference for all future Implementation Plans.
- Ensure operational users have sufficient read access without unnecessary write permissions.

All future modules must reference this document when defining authorization requirements.

---

# 2. RBAC Principles

The Bakery ERP uses **Permission-Based Authorization**, not Role-Based Authorization.

Users receive one Role.

Roles contain many Permissions.

Application authorization checks **Permissions**, never Roles.

Example:

```
User
    ↓
Role
    ↓
Permissions
    ↓
API Authorization
```

Example:

```
User
↓

ADMIN_GUDANG

↓

product.read
inventory.manage

↓

GET /products
```

# 3. Role Management Principles & Conceptual Distinction

## 3.1 Conceptual Distinction Guide
- **Role Code**: The technical, unique string identifier used in code, JWT claims, and database constraints (e.g., `PRODUKSI`). It is immutable and case-sensitive.
- **Display Name**: The friendly, business-representative label shown to users in the UI (e.g., *Production Staff*).
- **Permission**: The granular access right (e.g., `production.manage`) evaluated by backend guards and frontend visibility helpers.

## 3.2 Role Management Principles
- **Role Represents Business Function**: A Role directly corresponds to a real job title or operational function in a bakery organization (e.g., *Cashier*, *Outlet Staff*).
- **Business Roles Only**: Every Role must represent an actual business position or operational function inside the Bakery ERP. Future roles include `PURCHASING_OFFICER`, `FINANCE_ADMIN`, `OPERATIONS_MANAGER`. Generic roles such as `Other`, `Miscellaneous`, `General`, `Unknown`, or `Undefined` must never be introduced.
- **No Fallback/Other Roles**: When the system cannot classify a requested role, do NOT generate an "Other" role or generic role; instead, ask for human clarification or recommend creating a new business role if required.
- **Role Creation Rule**: Every new role must represent a real business function, have a clear responsibility, own a defined permission set, be documented in this Matrix, and be approved before implementation.
- **Permission Represents System Access**: A Permission defines granular capability to perform an action on a resource (e.g., `product.read`, `sales.manage`).
- **One Role Per User**: Each user in the ERP is assigned exactly one Role at any given time.
- **Many Permissions Per Role**: A Role contains multiple Permissions representing its operational duties.
- **Permission-Based Backend Authorization**: Backend controllers and middleware must authorize endpoints based solely on user Permissions, never by checking Role Codes. Roles function solely as permission containers.

## 3.3 Flow Diagram
```
SystemModule
  ↓
Permission
  ↓
RolePermission
  ↓
Role
  ↓
User
  ↓
Authorization
```

## 3.4 Role Lifecycle
```
Role
  ↓
User Assignment
  ↓
Permission Resolution
  ↓
Request Authorization
  ↓
Audit Trail
```
A Role in the Bakery ERP serves the following purposes:
- **User Assignment**: Assigned to a User to categorize their role within the organization.
- **Permission Resolution**: Determines the user's set of active Permissions based on the role mapping.
- **Request Authorization**: Invoked during authorization verification of incoming requests.
- **Audit Trail**: Referenced in audit logs for security, reporting, and traceability.

# 4. Architecture Decision Record (ADR)

### ADR-0015 – Role & Permission Strategy

##### Decision
- Role Codes are immutable. They are considered stable technical identifiers after Sprint 1.
- Permission Assignment is managed solely via database seeding (`seed.ts`) in Sprint 1.
- Backend authorizes requests based on Permission strings, never on Role Codes.

##### Reason
- **Consistency**: Guarantees a standardized, uniform authorization model.
- **MVP Simplicity**: Minimizes runtime complexity for the initial release.
- **Audit Log Integrity**: Secures historical logging metadata against shifting role definitions.
- **Reliability**: Eliminates runtime configuration errors and privilege escalation vectors.

##### Consequence
- No user interface or API exists in Sprint 1 to edit role permission assignments at runtime.
- Dynamic Role & Permission Management is deferred to a subsequent sprint as a separate, audited module.

### ADR-0016 – SystemModule Integration

##### Decision
- Introduce `SystemModule` as the database-level grouping parent for permissions.
- Move relation include logic to the repository layer to automatically return parent modules with permissions.
- Store metadata properties `icon` and `sortOrder` in `SystemModule` to support future UI grouping requirements.

##### Reason
- **Clean Grouping**: Decouples business domain categorization from static code mapping.
- **Encapsulation**: Promotes repository-oriented design by containing query relation mapping within `PermissionRepository`.
- **Extensibility**: Permits future UI components to dynamically group and display permissions by domain using native database attributes.

##### Consequence
- All permissions belong to exactly one `SystemModule`.
- Client queries fetching permissions receive associated `systemModule` details transparently.

### ADR-0017 - Business-Domain Permission Grouping

##### Decision
- Role Management renders permissions from metadata using the permanent hierarchy: **Business Domain -> Module -> Action**.
- Every active permission must have complete metadata: `domain`, `moduleKey`, `moduleName`, `action`, `displayName`, and `sortOrder`.
- Metadata columns may be nullable only for migration compatibility. The migration target is zero active permissions without complete metadata after seed/backfill.
- Legacy permissions must use an explicit deterministic compatibility mapping. They must never fall back to generic `Access` or `Audit` visual groups.
- Unmapped legacy permissions must be logged as warnings and grouped as `Unmapped Permissions` until a proper metadata mapping is approved.

##### Canonical Domains
1. Master Data
2. Procurement
3. Inventory
4. Production
5. Sales
6. Finance
7. System Administration
8. Reports
9. Settings

##### Reason
- Role Management must reflect ERP business domains, not technical or historical categories.
- Payment Term belongs under Master Data.
- Purchase Request, Purchase Order, Goods Receipt, and Purchase Return belong under Procurement as separate modules.
- Vendor Invoice belongs under Finance as a separate module.
- Permission codes and authorization behavior remain stable while UI grouping becomes metadata-driven.

##### Consequence
- Do not create `Access` or `Audit` as top-level Role Management business groups.
- Do not hardcode module-specific rendering in the Role Management UI.
- Seed scripts must update permission metadata idempotently and preserve custom role-permission assignments.

# 5. Permission Assignment Policy

For the duration of **Sprint 1**, the following policies govern how roles are assigned permissions:
- **Seed-Controlled Assignments**: All Role-to-Permission assignments are statically defined and managed via the database seeding script (`prisma/seed.ts`).
- **Immutable via UI**: Permission assignments are read-only in the UI. No dashboard or endpoint exists in Sprint 1 that allows modification of a role's permissions at runtime.
- **Stability Decision**: This is a deliberate architectural decision to ensure MVP stability, maintain consistent authorization structures, and prevent authorization misconfiguration.
- **Future Roadmap**: Dynamic Role-Permission Management (enabling admins to assign/revoke permissions via the UI) will be introduced in subsequent sprints as a separate, dedicated module complete with full audit logging and security validation.

# 6. Permission Naming Standard

Every business module follows the same naming convention.

## Read Permission

```
<module>.read
```

Allows users to:

- View list
- View detail
- Lookup
- Search
- Filter

Example

```
product.read
```

---

## Manage Permission

```
<module>.manage
```

Manage includes:

- Create
- Update
- Change Status
- Soft Delete

Manage automatically implies Read permission.

Developers **must not** check both:

```
product.read
product.manage
```

Checking

```
product.manage
```

already grants read capability.

# 8. Default Role Mapping

## OWNER

The Owner role is a global role template, but SaaS authorization applies it through `CompanyMembership`. `OWNER` in one Company does not grant access to another Company. For tenant-aware context, OWNER derives access to all non-deleted Outlets inside the active Company. Non-OWNER memberships use explicit `CompanyMembershipOutlet` assignments. During the compatibility phase, some legacy operational modules may still contain role-code based Owner bypasses; these are legacy behavior and must be migrated during Tenant Isolation Hardening before the ERP can claim full SaaS tenant isolation.

### Access Scope

OWNER receives **all operational permissions** across all domains **EXCEPT** system administration. System administration permissions are reserved for SUPER_ADMIN (platform-level) only.

### ✅ Granted Permissions (Operational Domains)

| Domain | Permissions |
|--------|-------------|
| **Master Data** | outlet.*, supplier.*, payment-term.*, category.*, product-group.*, uom.*, product.* |
| **Procurement** | procurement.pr.*, procurement.po.*, procurement.gr.*, procurement.return.* |
| **Inventory** | inventory.*, inventory.adjustment.*, inventory.stock-count.*, inventory.transfer.*, replenishment.* |
| **Production** | recipe.*, bom.*, production.*, production-order.* |
| **Distribution** | distribution.*, delivery-order.*, inter-outlet-transfer.* |
| **Sales & POS** | sales.*, shift.*, pos.* |
| **Finance** | finance.vendor-invoice.*, finance.accounts-payable.*, payment.*, expense.*, cashflow.* |
| **Reporting** | dashboard.read, report.* |
| **Settings** | setting.*, company.* |

### ❌ Excluded Permissions (System Administration — SUPER_ADMIN Only)

| Permission | Description |
|------------|-------------|
| `user.read`, `user.manage` | User management (create/edit/delete users) |
| `role.read`, `role.manage` | Role management (create/edit/delete roles, assign permissions) |
| `permission.read`, `permission.manage` | Permission catalog management |
| `audit.read` | Audit log access |
| `auth.manage` | Authentication configuration |

### Rationale

System administration permissions are platform-level concerns. SUPER_ADMIN (seeded separately, not tied to any company) manages user creation and role configuration for all companies. OWNER focuses on operational management within their own company.

**Implementation:** OWNER role is seeded with an explicit permission list (not `'ALL'` sentinel) that excludes the 8 system-administration permissions listed above. See `permissions.seed.ts` → `DEFAULT_ROLES` → OWNER.
