## 1. Context

The backend (NestJS + Fastify + raw SQL `pg` + node-pg-migrate) is mature (Sprints 1–4
complete, 790 tests passing). The frontend was greenfield — `frontend/` did not exist.

The frozen frontend baseline (docs 19, 23, 37, 38) is written entirely for **React 19 /
Next.js 15** (App Router, `page.tsx`, React Query, React Hook Form, Shadcn UI, `components/erp`
+ `components/ui`). During Tahap A profiling (see `project-context/2026-09-28.md`), the
User elected to build the frontend on **Vue 3** instead. This is a real conflict: the
React-based constitution cannot be applied verbatim to Vue.

## 2. Decision

### 2.1 Framework & Build (deviates from doc 23)

- **Vue 3** with `<script setup>` + **TypeScript**.
- **Vite** as the build tool (replaces Next.js App Router / Turbopack).
- Config-based routing via **Vue Router** (replaces file-system routing / `page.tsx`).

Rationale: the User owns frontend architecture decisions. Vue 3 + Vite gives a lean SPA that
talks to the existing REST API. Next.js SSR/RSC features are not required for an internal ERP
dashboard behind auth.

### 2.2 Final Stack

| Concern | Choice | React-baseline equivalent |
| --- | --- | --- |
| Framework | Vue 3 (`<script setup>` + TS) | React 19 |
| Build | Vite | Next.js 15 |
| Styling | Tailwind CSS (darkMode: `class`) | Tailwind v4 |
| UI primitives | Reka UI (shadcn-vue pattern) | Shadcn UI (Radix) |
| Forms & validation | VeeValidate + Zod | React Hook Form + Zod |
| Server state | TanStack Query for Vue | TanStack Query (React) |
| Client state | Pinia | Zustand |
| Routing | Vue Router (config-based + guards) | Next App Router |
| HTTP | Axios | Axios |
| Data grid | TanStack Table for Vue | TanStack Table (React) |
| Icons | lucide-vue-next | lucide-react |

### 2.4 ERP UI Foundation — rebuilt for Vue (mirrors doc 19 layering)

The 4-layer boundary from doc 19 is preserved, remapped to Vue:

```
View / Page (views/, config-routed)
  -> Feature Components (<feature>/components/)
    -> ERP UI Foundation (components/erp/*)   <- Vue rebuild
      -> Reka UI primitives (components/ui/*)   <- wrapped, never used raw in features
```

**Phased build:** only the core subset is built now (Layout, Inputs, Button, Form, Feedback,
Status, DataTable foundation). The full ~40-component catalog from doc 23 is deferred and
built on demand per module.

**Foundation components built so far** (grows per module; reuse-first before adding new):
- Layout: `ERPPage`, `ERPPageHeader`, `ERPContent`, `ERPCard`
- Inputs: `ERPInput`, `ERPPasswordInput` (wrap `PrimitiveInput`)
- Button: `ERPButton` (variants primary/secondary/ghost/danger, `iconOnly`, `loading`)
- Form: `ERPForm`, `ERPFormField` (VeeValidate `useField`), `ERPFormSection`, `ERPFormActions`
- Feedback: `ERPLoading`, `ERPEmpty`, `ERPNotification` (+ notification store)
- Status: `ERPStatusBadge` (tones: primary/success/danger/muted/neutral)
- Data: `ERPDataTable` (generic `T extends object`, columns + `cell-<key>` slot,
  loading/empty/error states, `row-clickable`)
- Overlay: `ERPDrawer` (side panel for detail/forms) wrapping `PrimitiveDialog` (ui layer,
  Reka UI Dialog)

Not yet built (add when a module needs them): `ERPFormDialog`/modal form,
`ERPDeleteDialog` (confirm), `ERPTablePagination`, `ERPSearchInput`/filter bar,
`ERPSelect`/`ERPCombobox` (dropdown). These are next-up for the Users CRUD module.

## 3. Document Disposition

### Forked for Vue (React-specific — do NOT apply verbatim)
- **doc 19** frontend-constitution → layering concept kept; React/Next specifics (App Router,
  `page.tsx`, `'use client'`, Shadcn import rules) reinterpreted for Vue SFC + Vue Router.
- **doc 23** architecture-version → frontend baseline overridden by §2.2 above.
- **doc 37** react-query-standard → concepts (query keys, invalidate-on-write, stale time)
  reused via TanStack Query **for Vue** composables.
- **doc 38** form-standard → RHF patterns re-expressed as VeeValidate + Zod.

### Framework-neutral (kept as-is, still authoritative)
- **doc 18** frontend-design-system → tokens/radius/density are CSS-level, reused directly.
- **doc 8** api-contract → REST envelope + versioning (see §4 correction).
- **doc 16** role-permission-matrix → permission model (`domain.action`, `.manage` implies
  `.read`, isSuperAdmin bypass) enforced in a Vue `usePermission()` composable + router guard.

## 4. Correction to doc 8 (api-contract) — verified against real backend

Doc 8 is **inaccurate** for auth. The verified real contract (do not follow doc 8 for these):

- `POST /api/v1/auth/login` `{ email, password(min 8) }` → `{ success, data: { accessToken, refreshToken } }`. **No `user` object.**
- `PUT /api/v1/auth/refresh` `{ refreshToken }` → `{ success, data: { accessToken } }`.
- `DELETE /api/v1/auth/logout` `{ refreshToken }` → `{ success, data: null }`.
- **No `GET /auth/profile`.** User identity & permissions are **decoded from the JWT**:
  `sub`, `email`, `companyId`, `isSuperAdmin`, `permissions: string[]`, `roleCode`.
- `GET /api/v1/companies/me` → `{ success, data: { id, code, name, slug, address, phone, isActive } }`.
- List envelope: `{ success, data: T[], meta: { page, limit, total, totalPages } }` — `data` is the array directly.
- **Dashboard endpoints do NOT exist yet.** UI renders a clean empty-state and flags the need
  for `GET /dashboard/owner` and `GET /dashboard/outlet`. No mock data.

## 5. Consequences

- Frontend engineers follow this ADR + docs 18/8/16 for the frontend; docs 19/23/37/38 are
  read as **concept references**, not literal React rules.
- A future Vue-specific frontend constitution may formalize the rebuilt ERP UI Foundation;
  until then this ADR governs.
- Backend contracts, permissions, and routing are unchanged by this ADR.
