# 37. React Query Standard

This document establishes the patterns for client-side state synchronization, query caching, and mutations using TanStack React Query in the Bakery ERP.

---

## 1. Query Key Convention

To maintain cache consistency and ensure precise invalidation triggers, query keys must use a structured array convention:

```typescript
// Pattern: [domain, entity, action, variables]
export const purchaseRequestKeys = {
  all: ['procurement', 'purchase-requests'] as const,
  lists: () => [...purchaseRequestKeys.all, 'list'] as const,
  list: (filters: Record<string, any>) => [...purchaseRequestKeys.lists(), filters] as const,
  details: () => [...purchaseRequestKeys.all, 'detail'] as const,
  detail: (id: string) => [...purchaseRequestKeys.details(), id] as const,
};
```

---

## 2. Standard Query Hooks

Query hooks must encapsulate fetching, error mapping, and configuration parameters:

```typescript
import { useQuery } from '@tanstack/react-query';
import { purchaseRequestService } from '../services/purchase-request.service';
import { purchaseRequestKeys } from './keys';

export function useGetPurchaseRequests(filters: Record<string, any>) {
  return useQuery({
    queryKey: purchaseRequestKeys.list(filters),
    queryFn: () => purchaseRequestService.list(filters),
    placeholderData: (previousData) => previousData, // keep UI smooth during transitions
    staleTime: 5 * 1000, // 5 seconds
  });
}
```

## 3. Standard Mutation & Invalidation Hooks

Mutations must trigger automatic cache invalidation of corresponding affected keys upon success and must provide explicit user feedback. Backend validation messages must be surfaced when safe and useful; failed mutations must not silently redirect or discard the user's current state.

```typescript
import { useMutation, useQueryClient } from '@tanstack/react-query';
import { purchaseRequestService } from '../services/purchase-request.service';
import { purchaseRequestKeys } from './keys';
import { toast } from '@/components/erp/toast';

export function useCreatePurchaseRequest() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (data: any) => purchaseRequestService.create(data),
    onSuccess: (response) => {
      // Invalidate all purchase request list caches
      queryClient.invalidateQueries({ queryKey: purchaseRequestKeys.lists() });
      toast.success('Purchase request created successfully.');
    },
    onError: (error: any) => {
      toast.error(error.response?.data?.message || 'Failed to create purchase request.');
    }
  });
}
```

Rules:
- Use the shared API error extraction helper instead of duplicating Axios response parsing in feature components.
- Use domain-specific mutation hooks for domain-specific success and fallback error text.
- Invalidate only directly affected query keys. Prefer `detail(id)`, `comments(id)`, or `attachments(id)` over broad global invalidation when the resource is independently queried.
- On failed mutations, do not perform success invalidation, redirect, or clear the user's form/document state.

## 4. Optimistic Update Pattern

For high-frequency toggle actions (e.g. archiving an active vendor or toggle priority), follow this pattern:

```typescript
export function useToggleVendorStatus() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (id: string) => vendorService.toggleStatus(id),
    onMutate: async (id) => {
      // Cancel outgoing refetches so they don't overwrite our optimistic update
      await queryClient.cancelQueries({ queryKey: vendorKeys.all });

      // Snapshot the previous value
      const previousVendors = queryClient.getQueryData(vendorKeys.lists());

      // Optimistically update the cache list
      queryClient.setQueryData(vendorKeys.lists(), (old: any) => {
        if (!old) return old;
        return {
          ...old,
          data: old.data.map((item: any) => 
            item.id === id ? { ...item, status: item.status === 'ACTIVE' ? 'INACTIVE' : 'ACTIVE' } : item
          )
        };
      });

      // Return context with snapshot value
      return { previousVendors };
    },
    onError: (err, id, context) => {
      // Rollback to previous snapshot if mutation fails
      if (context?.previousVendors) {
        queryClient.setQueryData(vendorKeys.lists(), context.previousVendors);
      }
      toast.error('Failed to update vendor status.');
    },
    onSettled: () => {
      // Always refetch to sync with server truth
      queryClient.invalidateQueries({ queryKey: vendorKeys.lists() });
    }
  });
}
```

## 5. UI Skeletons & Loading States

- **Use of ERPLoading**: Tables and list views must render the `ERPLoading` skeleton wrapper during the initial load (`isLoading` is true).
- **Secondary Actions**: Buttons triggering mutations must toggle to `disabled` and show loading spinners when `isPending` is true.
