# 49. ADR — Dynamic Role Management

**Status:** Accepted
**Date:** 2026-09-30
**Supersedes (partial):** ADR-0015 §"Permission Assignment Policy" (Sprint 1 freeze)
**Related:** doc 16 (role-permission-matrix), doc 35 §3 (permission metadata), doc 44 (master-data dependency), doc 24 §10.9 (SaaS tenant), doc 47 (TailAdmin frontend)

---

## 1. Context

ADR-0015 (doc 16 §4/§5) membekukan role–permission management sebagai **read-only via seed** untuk Sprint 1, dengan catatan bahwa "Dynamic Role & Permission Management" ditunda ke sprint berikutnya sebagai modul terpisah yang di-audit.

Kebutuhan bisnis sekarang menuntut modul itu diaktifkan: pemilik company (OWNER) harus bisa membuat, mengubah, dan menghapus role di dalam company-nya, serta menyusun permission tiap role melalui UI. Frontend TailAdmin (doc 47) menjadi tempat implementasinya.

Keputusan ini disetujui user pada 2026-09-30 dan dicatat lewat ADR ini (memenuhi syarat doc 16 §4 & doc 20 §8 bahwa perubahan kebijakan konstitusi memerlukan ADR atau persetujuan eksplisit user).

---

## 2. Decision

### 2.1 Membuka freeze
Role Management menjadi **dinamis** (CRUD via API + UI), menggantikan kebijakan read-only Sprint 1. Permission catalog tetap didefinisikan lewat seed (source of truth kode permission tidak berubah); yang menjadi dinamis adalah **assignment** permission ke role dan **lifecycle** role per company.

### 2.2 Dua konsep identitas yang dibedakan
- **SUPER_ADMIN** — user platform (`company_id = NULL`, `is_super_admin = TRUE`). Full-permission via bypass guard. TIDAK pernah ditampilkan di layar Role Management. Berperan sebagai jaring pengaman dan dapat menyesuaikan role company mana pun.
- **OWNER** — role company (pemilik). Boleh disesuaikan (nama/deskripsi/permission) oleh SUPER_ADMIN maupun oleh dirinya sendiri (karena memiliki `role.manage`). Digunakan untuk mengatur role & permission level lain di dalam company-nya sendiri.

### 2.3 Guardrails (WAJIB ditegakkan di backend, bukan hanya UI)
1. **OWNER `role.manage` permanen**: role dengan `code = 'OWNER'` selalu mempertahankan permission `role.manage`. Bila payload mencoba menghapusnya, backend memaksa tetap ada (defense-in-depth). Di UI, checkbox `role.manage` untuk OWNER ditampilkan tercentang + disabled dengan tooltip "Wajib untuk Owner".
2. **OWNER tidak dapat dihapus**: DELETE role ber-`code = 'OWNER'` ditolak.
3. **`code` role immutable** setelah dibuat: hanya `name`, `description`, dan set permission yang dapat diedit. Menjaga stabilitas identifier (selaras ADR-0015 tentang role code stabil) dan validitas guardrail OWNER.
4. **Guard endpoint write = `role.manage`**: dimiliki OWNER; SUPER_ADMIN bypass. OWNER dapat mengelola role lain di company-nya.
5. **Dependency protection (doc 44)**: DELETE role ditolak (409) bila masih dipakai user aktif.
6. **Tenant isolation (doc 24 §10.9)**: semua operasi role & assignment company-scoped; role platform (company_id NULL / SUPER_ADMIN) TIDAK muncul di list company dan tidak dapat disentuh via endpoint company.
7. **Tanpa eskalasi**: permission yang dapat diberikan ke role hanya yang terdaftar di katalog permission global; tidak ada pembuatan permission baru dari UI.

### 2.4 UI (permission picker)
- Permission dirender dari metadata: **Business Domain → Module → Action** (doc 35 §3).
- Checkbox **per action**, dikelompokkan per **modul**, dikelompokkan dalam kartu **per domain** yang dibedakan **warna** menggunakan token Tailwind TailAdmin (brand/success/warning/error/blue-light/orange, dst — TIDAK hex hardcode).
- 9 canonical domains: System Administration, Master Data, Procurement, Inventory, Production, Sales, Finance, Reports, Settings.

## 3. API Surface

- `GET /api/v1/permissions` — katalog permission + metadata (domain, moduleKey, moduleName, action, sortOrder). Guard: `role.read` (cukup untuk merender picker; alternatif `permission.read`).
- `POST /api/v1/roles` — create role (code/name/description) + set permission awal. Guard `role.manage`.
- `PUT /api/v1/roles/:id` — update name/description + full-sync permission. Guard `role.manage`. Enforce guardrail OWNER.
- `DELETE /api/v1/roles/:id` — delete role. Guard `role.manage`. Tolak OWNER & role yang dipakai user (409).
- `GET /api/v1/roles`, `GET /api/v1/roles/:id` — sudah ada; list mengecualikan role platform.

Response tetap mengikuti envelope standar `{ success, data, meta? }`.

---

## 4. Consequences

- **Positif**: OWNER mandiri mengelola RBAC company-nya; konsisten dengan metadata permission yang sudah kaya; tidak mengubah kode permission (hanya assignment).
- **Trade-off**: role menjadi mutable → audit logging assignment menjadi penting (ikuti pola audit modul lain bila tersedia; minimal SYSTEM comment/log perubahan bila infrastruktur ada).
- **Risiko self-lockout** OWNER dimitigasi oleh guardrail `role.manage` permanen + SUPER_ADMIN sebagai jaring pengaman.
- **Dokumen terdampak**: doc 16 §5 (kebijakan freeze) kini di-relaksasi oleh ADR ini; doc 13 checklist Role Management perlu diperbarui setelah implementasi.

---

## 5. Verification

- Backend: `npx tsc --noEmit` bersih; unit test mencakup create/update/delete, guardrail OWNER (role.manage dipaksa, OWNER tak terhapus), code immutable, delete-in-use 409, tenant scoping.
- Frontend: `npm run build` hijau; picker merender grouped-by-domain berwarna; checkbox OWNER role.manage disabled+checked.
