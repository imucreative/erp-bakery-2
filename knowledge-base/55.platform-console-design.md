## 1. Tujuan & Batasan

Platform console adalah area **platform-level** untuk operator SaaS (Super Admin) —
**bukan** area tenant. Tujuannya mengelola tenant (perusahaan) dan identitas lintas
perusahaan tanpa mencampurnya dengan layar ERP yang bersifat `company-scoped`.

Batasan:

1. Super Admin **tidak memiliki konteks perusahaan** (`users.company_id = NULL`),
   sehingga seluruh query tenant (`company_id = $x`) tidak berlaku untuknya.
2. Platform console bersifat **read-only terhadap data operasional tenant**
   (produk, stok, penjualan, pembelian, produksi, laporan).
3. Tidak ada mutasi data operasional tenant dari platform console. Mutasi identitas
   dan akses lintas tenant diperbolehkan melalui endpoint platform khusus dan audit.
   Bila di masa depan
   dibutuhkan (impersonation/support action), wajib melalui alur eksplisit + audit log.

## 2. Model Akses (dua level)

| Level | Aktor | Konteks data | Penanda | Penjaga |
| --- | --- | --- | --- | --- |
| **Tenant** | OWNER, SUPERVISOR_OUTLET, ADMIN_GUDANG, PRODUKSI, KASIR, … | Satu `company_id` | JWT `companyId` + `permissions[]` | `PermissionsGuard` + `@RequirePermission()` |
| **Platform** | SUPER_ADMIN | Lintas tenant | JWT `isSuperAdmin = true` | `PermissionsGuard` + `@SuperAdminOnly()` |

Aturan:

- `users.is_super_admin = TRUE` → bypass semua permission check (doc 16).
- Super Admin **tidak** memakai permission code untuk route platform — route platform
  ditandai `@SuperAdminOnly()`, bukan `@RequirePermission()`.
- Endpoint tenant tetap `company-scoped`; Super Admin yang memanggilnya akan ditolak
  dengan `AUTHORIZATION.NO_COMPANY_CONTEXT`.

## 3. Keputusan Desain

### 3.1 Super Admin = operator platform, bukan "owner super"

Super Admin tidak "masuk sebagai owner" di dalam tenant. Ia punya konsol sendiri.
Login Super Admin diarahkan ke `/platform/companies`, dan router **mengurung**-nya
di area `meta.platform` (tidak bisa membuka layar ERP).

### 3.2 Read-only terhadap data tenant operasional

**Disetujui User (2026-11-03).** Alasan:

- Data operasional tenant adalah milik tenant; perubahan oleh platform berisiko
  merusak jejak audit dan integritas stok/akuntansi.
- Kebutuhan "melihat" sudah tercukupi oleh laporan tenant; kebutuhan "memperbaiki"
  sebaiknya lewat impersonation yang tercatat, bukan akses senyap.

**Pengecualian (identitas & akses):** pembuatan user, penetapan role, dan katalog
permission adalah pekerjaan platform menurut doc 16. Penulisan wajib melalui
endpoint `/platform/*` (bukan endpoint tenant) dan **wajib** masuk audit log.
Riwayat v1 masih read-only untuk user; v2 sudah menyediakan CRUD user dan assignment
role company dengan audit; v3 menambahkan CRUD role company dari `/platform/roles`
(katalog permission tetap read-only dan hanya bisa dipilih, bukan dibuat/diubah).

### 3.3 2FA untuk akun Super Admin

**Disetujui User sebagai persyaratan; v1 SUDAH DIIMPLEMENTASIKAN (2026-11-03).**

- TOTP RFC 6238 (HMAC-SHA1, 6 digit, periode 30 detik, toleransi ±1 langkah)
  + 10 kode recovery sekali-pakai.
- Kolom `users`: `two_factor_secret` (**AES-256-GCM**, kunci dari env
  `TOTP_ENCRYPTION_KEY` 64 hex char), `two_factor_enabled`,
  `two_factor_recovery_codes` (JSON array bcrypt hash), `two_factor_confirmed_at`.
- Login dua langkah: `POST /auth/login` mengembalikan `{ mfaRequired: true, mfaToken }`
  (token berumur 5 menit, purpose `mfa`, tidak bisa dipakai sebagai access token),
  lalu `POST /auth/mfa/verify` menukarnya menjadi access/refresh token.
- Endpoint pengelolaan (authenticated): `GET /auth/2fa/status`, `POST /auth/2fa/setup`,
  `POST /auth/2fa/enable`, `POST /auth/2fa/disable` (butuh kode valid).
- Frontend: langkah kode 2FA di halaman Sign In, serta bagian **Security** di halaman
  Profile (`Security.vue`) untuk setup, recovery codes, enable/disable.
- Lupa perangkat → tidak ada self-service reset; gunakan salah satu kode recovery,
  atau break-glass lewat DB (`two_factor_enabled = FALSE`).
- **Enforcement:** semua route `@SuperAdminOnly()` (konsol platform) menolak akses
  (`403 AUTHORIZATION.MFA_REQUIRED`) selama 2FA pada akun Super Admin belum aktif.
  Endpoint enroll (`/auth/2fa/*`) sengaja tidak di-gate agar operator bisa
  mengaktifkannya. Frontend mengarahkan ke halaman Profile (kartu 2FA) saat gate ini
  menolak.
- **Rate limit (anti brute-force):** `POST /auth/login` 10 percobaan/menit per IP;
  `POST /auth/mfa/verify` 5 percobaan/menit per IP (counter di-reset saat berhasil) →
  `429 Too Many Requests`. Limiter in-memory per proses (ganti ke Redis bila API
  di-scale horizontal).
- Catatan: 2FA tetap **opsional untuk user tenant** (belum dipaksa oleh kebijakan).

### 3.4 Audit log (wajib sebelum mutasi platform)

Tabel `audit_logs` (actorId, actorEmail, action, entity, entityId, companyId, ip,
userAgent, metadata, createdAt). Semua aksi platform (termasuk `PATCH` status company)
harus menulis entri audit. Riwayat v1 hanya menyebut `companies.updated_at` untuk
perubahan status company; timestamp ini **bukan audit log penuh**. v2 sudah mencatat
create/edit/delete user ke `audit_logs`; jangan memperluas klaim tersebut menjadi
cakupan audit seluruh aksi platform. Audit viewer masih pending.

## 4. Implementasi v1 (2026-11-03)

### 4.1 Backend

| Komponen | Detail |
| --- | --- |
| `decorators/super-admin-only.decorator.ts` | `@SuperAdminOnly()` → metadata `superAdminOnly` |
| `guards/permissions.guard.ts` | Route `@SuperAdminOnly()`: wajib `isSuperAdmin` dan 2FA aktif, tanpa permission code |
| `Domains/companies/CompanyRepository.ts` | `listCompanies()`, `setCompanyActive()` |
| `Infrastructures/repository/CompanyRepositoryPostgres.ts` | Query list (search name/code/slug, `userCount`), update status |
| `Domains/platform/PlatformRepository.ts` | Kontrak cross-tenant read-only |
| `Infrastructures/repository/PlatformRepositoryPostgres.ts` | `listUsers()` lintas perusahaan (join companies + roles) |
| `api/companies/company.controller.ts` | `GET /companies`, `PATCH /companies/:id/status` |
| `api/platform/platform.controller.ts` | `GET /platform/users` |
| `api/platform/platform.controller.ts` | `GET /platform/companies/:companyId/roles`, `POST/PUT/DELETE /platform/users` |
| `PlatformRepositoryPostgres` | Create via user use case; edit/reassign/status/delete + audit log |

**Kontrak API**

```text
GET   /api/v1/companies?page&limit&search      → SUPER_ADMIN, list + meta
PATCH /api/v1/companies/:id/status             → { isActive: boolean }
GET   /api/v1/platform/users?page&limit&search&companyId → SUPER_ADMIN, list + meta
GET   /api/v1/platform/companies/:companyId/roles              → SUPER_ADMIN, role list + userCount
GET   /api/v1/platform/companies/:companyId/roles/:roleId      → SUPER_ADMIN, role detail + permissions
POST  /api/v1/platform/companies/:companyId/roles              → SUPER_ADMIN, create role + permissions
PUT   /api/v1/platform/companies/:companyId/roles/:roleId      → SUPER_ADMIN, update + full-sync permissions
DELETE /api/v1/platform/companies/:companyId/roles/:roleId     → SUPER_ADMIN, delete (OWNER/in-use → 409)
GET   /api/v1/platform/permissions                             → SUPER_ADMIN, permission catalog
POST  /api/v1/platform/users                                     → SUPER_ADMIN, create + assign company/role
PUT   /api/v1/platform/users/:id                                → SUPER_ADMIN, edit/reassign/status
DELETE /api/v1/platform/users/:id                               → SUPER_ADMIN, soft-delete
```

Catatan: `GET /companies/me` tetap ada untuk user tenant (mengembalikan `null` bila
tidak punya company, sehingga Super Admin tidak error).

3. Login sebagai Super Admin tidak mengikuti `?redirect=` (selalu ke konsol).
