This document is the **canonical frontend architecture constitution** for the Bakery ERP project. All future frontend implementation rules, features, and refactorings must reference and adhere to this document instead of duplicating or redefining architectural rules elsewhere.

---

## 1. Purpose

The Frontend Constitution establishes a strict, predictable layer boundary to:
- Guarantee visual, operational, and coding consistency across all ERP modules.
- Prevent duplicate UI rendering paths and ad-hoc layouts.
- Enforce clean separation between page-level business orchestration, feature components, and the foundational component library.

---

## 2. Layered Architecture

The frontend is structured in four strict, isolated layers:

```
┌─────────────────────────────────────────────────────────┐
│ Page Composition Layer (app/(dashboard)/<feature>/)    │
└────────────────────────────┬────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────┐
│ Feature Components Layer (<feature>/components/)        │
└────────────────────────────┬────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────┐
│ ERP UI Foundation Layer (components/erp/)               │
└────────────────────────────┬────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────┐
│ Shadcn UI Primitives Layer (components/ui/)             │
└─────────────────────────────────────────────────────────┘
```

1. **Page Composition Layer (`page.tsx`)**: Orchestrates data fetching (using services and React Query), manages modal open/close states, and maps inputs. No raw HTML, table grids, forms, or dialog wrappers.
2. **Feature Components Layer (`components/`)**: Houses feature-specific tables (`<feature>-table.tsx`), dialogs (`<feature>-form-dialog.tsx`), and filters (`<feature>-filter-bar.tsx`). Uses ERP UI Foundation components exclusively to render UI.
3. **ERP UI Foundation Layer (`components/erp/`)**: Reusable, atomic wrapper components (e.g. `ERPButton`, `ERPInput`) defining standard classes, styling, loading states, and dark mode toggles.
4. **Shadcn UI Primitives Layer (`components/ui/`)**: Third-party primitive templates (Radix wrapper utilities) styled using Tailwind classes.

---

## 3. Dependency Rules

### Allowed Imports:
- Page files (`page.tsx`) may import from `services/`, `hooks/`, `stores/`, `types/`, and the local `components/` subfolder.
- Feature components (`components/*`) may import from `components/erp/*` and `lucide-react` (for icons).

### Forbidden Imports:
- Page files (`page.tsx`) **must never** import from `@/components/ui/*` or `@/components/erp/*` directly (except container layouts like `ERPPage`, `ERPContent`).
- Feature components **must never** import directly from `@/components/ui/*`. All Shadcn UI primitives must be isolated and wrapped inside the ERP UI Foundation layer.
- Components must never import libraries not approved in the [23.architecture-version.md](file:///d:/antigravity/erp-bakery-2/knowledge-base/23.architecture-version.md) stack baseline.

## 4. Feature Folder Structure

Every module in `app/(dashboard)/<feature>` must follow this standard structure:

```
app/(dashboard)/<feature>/
├── page.tsx                    # Controller & state manager
└── components/                 # View components
    ├── index.ts                # Entrypoint exports
    ├── <feature>-columns.tsx   # Header cell filters and cell renderers
    ├── <feature>-delete-dialog.tsx # Delete confirmation overlay
    ├── <feature>-filter-bar.tsx # Toolbar inputs and filters
    ├── <feature>-form-dialog.tsx # Create/Edit form modal
    ├── <feature>-header.tsx     # View title and main buttons
    └── <feature>-table.tsx      # Table grid and pagination container
```

---

## 5. UI Foundation Rules

- **Mandatory ERP Components**: All form controls, buttons, tables, loaders, badges, and drawers must use the appropriate `ERP` prefix baseline component from `components/erp/*`.
- **Prohibited Direct Primitive Usage**: Direct HTML elements like `<button>`, `<input>`, `<textarea>`, `<select>`, `<checkbox>` or raw Radix/Shadcn primitives must not be used inside feature components.

---

## 6. Component Ownership & Responsibilities

- **page.tsx**: Manages states (open/close modals, selected data items, current pagination indices) and triggers data-fetching services. Passed values are bound down to components as props.
- **feature components**: Stateless view renderers. They receive data and event hooks, build layout combinations (e.g. mapping fields inside form section capsules), and notify `page.tsx` of changes.
- **ERP components**: Universal atomic primitives. They handle theme styling (`TOKENS`), loading animations, error messages, and baseline configurations.

---

## 7. Development & Consistency Rules

- **How new modules must be created**: New modules must copy the exact structure of existing feature components (e.g. `outlets` or `suppliers`), register its endpoints inside the repo layer, configure routing, and compose the interface using ERP foundation parts.
- **How existing modules must be extended**: Additional tabs, filter actions, or form inputs must be placed inside the existing feature component subfiles (`<feature>-filter-bar.tsx` or `<feature>-form-dialog.tsx`) and mapped via props.
- **Reuse-first**: Search the ERP UI Foundation library before styling or creating custom sub-components.
- **No duplicated UI / patterns**: If a visual pattern is already defined in one module (e.g. table pagination), replicate the pattern exactly using the same component properties.

---

## 8. Governance & Modifications

These rules represent a permanent element of the Project Constitution. Future modifications, additions of new reusable components, or modifications of dependency guidelines require:
- An approved **Architecture Decision Record (ADR)**, or
- Explicit user approval.
