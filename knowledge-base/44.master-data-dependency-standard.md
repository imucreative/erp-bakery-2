# 44. Master Data Dependency Standard

This document defines the mandatory referential integrity and dependency protection standard for Bakery ERP master data.

## Core Rule

A master data record that is referenced by active dependent master data or active/open transactional data must remain valid and active.

Protection must be enforced by:

- Database constraints where appropriate.
- Backend dependency validation.
- Service-level business rules.
- Frontend capability and dependency feedback.

Frontend validation is UX only. Backend and database rules remain the source of truth.

## Protected Operations

### Delete and Soft Delete

Delete or soft-delete is blocked when the record:

- Is referenced by active dependent master data.
- Is referenced by transactional documents.
- Is assigned to active users.
- Would break historical document readability or audit identity.

### Deactivation

Changing `isActive` from `true` to `false` is blocked when the record:

- Is used by active dependent master data.
- Is required by an open or active transaction.
- Is assigned to an active user.
- Would create invalid operational configuration.

Reactivation is allowed only when normal permission, scope, and uniqueness rules pass.

## Historical Data

Historical transactional references must never be broken.

Inactive master data:

- Must remain readable in historical documents.
- Must not be selectable for new transactions.
- Must not disappear from existing documents.

Documents must use snapshots where the business document requires historical values to remain stable.

Inventory Stock Opname references must remain readable after completion. Outlets referenced by non-terminal Stock Opname records (`DRAFT`, `COUNTING`, `SUBMITTED`, `APPROVED`) must not be deleted or deactivated, and inventory mutations for a counted outlet are blocked while the count is actively locked (`COUNTING`, `SUBMITTED`, `APPROVED`).

## Dependency Evaluation

All protected modules must use the shared backend dependency protection service instead of duplicating validation logic in controllers.

Required service capabilities:

- `evaluateDependencies(entityType, entityId)`
- `evaluateBatch(entityType, entityIds)`
- `canDelete(entityType, entityId)`
- `canDeactivate(entityType, entityId)`
- `assertCanDelete(entityType, entityId)`
- `assertCanDeactivate(entityType, entityId)`

The standardized dependency result is:

```json
{
  "canDelete": false,
  "canDeactivate": false,
  "dependencies": [
    {
      "entity": "StockOpname",
      "count": 3,
      "blocking": true,
      "reason": "Outlet is used by active Stock Opname records"
    }
  ]
}
```

## Error Contract

Blocked delete/deactivate operations must return:

- HTTP status: `409 Conflict`
- Error code: `MASTER_DATA_IN_USE`

```json
{
  "success": false,
  "code": "MASTER_DATA_IN_USE",
  "message": "Outlet cannot be deactivated because it is used by active Stock Opname records.",
  "dependencies": [
    {
      "entity": "StockOpname",
      "count": 3,
      "blocking": true,
      "reason": "Outlet is used by active Stock Opname records"
    }
  ],
  "errors": []
}
```

## Frontend Behavior

Master data list and detail responses should include additive metadata:

```json
{
  "capabilities": {
    "delete": false,
    "deactivate": false
  },
  "dependencySummary": {
    "StockOpname": 3
  }
}
```

Frontend modules must:

- Disable or hide delete actions when `capabilities.delete` is false.
- Disable deactivation controls when `capabilities.deactivate` is false.
- Keep reactivation available when permission and backend rules allow it.
- Show dependency explanations in tooltips, dialogs, or notifications.
- Handle `409 MASTER_DATA_IN_USE` consistently.
- Refresh affected rows after successful or failed mutation attempts.

## Performance Standard

Dependency checks must:

- Use count or existence queries.
- Avoid loading full dependent records.
- Avoid N+1 checks in list pages by using batch evaluation or aggregate counts.
- Use indexes on frequently checked foreign keys and status fields.

## Database Strategy

Master data relations used by business documents should use `Restrict` or `NoAction` semantics. Cascade is allowed only for true aggregate children, such as:

- Purchase Request to its items, approvals, comments, attachments, and history.
- Purchase Order to its items, approvals, comments, attachments, and history.
- User to session records when session cleanup is intentional.

Do not introduce destructive migrations for dependency protection.

## Testing Requirements

Each protected master data module must test:

- Delete succeeds when no blocking dependency exists.
- Delete fails with `MASTER_DATA_IN_USE` when a blocking dependency exists.
- Deactivate succeeds when no active dependency exists.
- Deactivate fails with `MASTER_DATA_IN_USE` when an active dependency exists.
- Historical references remain readable.
- Inactive records are excluded from new transaction lookup endpoints.
- Direct API calls cannot bypass dependency protection.
