## [Sprint 3 - Fase 1] Fondasi Inventory (Batch + Movement + Stock-On-Hand + FEFO) — Kiro (Auto model)

User meminta lanjut Sprint 3 (Inventory). Karena lingkup domain inventory sangat besar (baca `knowledge-base/27.inventory-domain.md` — 30 aturan bisnis: FEFO, batch identity, immutable ledger, concurrency, adjustment/opname/transfer lifecycle, dashboard, reconciliation), saya putuskan membangun **bertahap**: Fase 1 = fondasi read + FEFO engine yang menjadi tulang punggung semua fitur transaksional; Fase 2 (adjustment/opname/transfer/dashboard) menyusul.

Keputusan arsitektur penting yang diambil dari dokumen domain:
- **Outlet-native**: TIDAK ada warehouse layer. Batch & movement langsung scoped ke outlet → company.
- **Batch identity**: `outlet + product + batch_number + lot_key` (lot_key = normalized nullable-safe lot). Diimplementasikan sebagai unique constraint DB.
- **qty_available authoritative** untuk Stock-On-Hand (rule #8) — bukan hasil SUM ledger tiap request.
- **inventory_movements immutable ledger** (rule #9) + deterministic source key untuk idempotency (rule #5) via partial unique index dengan COALESCE uuid sentinel.
- **Negative-stock ban** (rule #2) diterapkan di dua lapis: CHECK constraint DB `qty_available >= 0` dan validasi di service.
- **Concurrency-safe mutation** (rule #6): postMovements pakai transaksi eksplisit `BEGIN` + `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` + `SELECT ... FOR UPDATE` sehால batch balance + ledger append commit atomik.
- **FEFO** (rule #1): ACTIVE, non-expired (expired_date >= businessDate agar same-day tetap valid, rule #14), qty>0, urut nearest-expiry; throw INSUFFICIENT_STOCK bila tak cukup.

Yang dibangun (mengikuti pola Clean Architecture modul Product):
- Migrasi 1700000000014 (inventory_batches) & 1700000000015 (inventory_movements).
- Domain: `movementTypes.ts`, `batchStatus.ts` (+ classifyExpiry, INVENTORY_EXPIRY_SOON_DAYS=30), entities InventoryBatch (+normalizeLotKey) & InventoryMovement, abstract InventoryRepository (getStockOnHand, getLedger, getBatches, getBatchById, planFefoAllocation, postMovements).
- Applications: GetStockOnHandUseCase, GetStockLedgerUseCase, GetBatchesUseCase (attach expiryState per row), PlanFefoAllocationUseCase (validasi qty>0 finite).
- Infrastructures: InventoryRepositoryPostgres (raw SQL, transaksi ACID) + wiring DI di InfrastructureModule (InventoryRepository + 4 use case, provider + export).
- Interfaces: InventoryController (GET stock-on-hand, ledger, batches, batches/:id) semua `inventory.read`, 3 DTO query, InventoryModule, didaftarkan di app.module + Swagger tag 'Inventory' di main.ts.
- Error codes inventory + FEFO di DomainErrorTranslator.
- Unit test semua layer: entity, batchStatus, movementTypes, 4 use case, repository (FEFO nearest-expiry + insufficient, postMovements inbound/insufficient/notfound/duplicate via mock client) + tambahan case translator.

## [Sprint 3 - Fase 2A] Stock Adjustment (lifecycle + posting authoritative) — Kiro (Auto model)

Lanjut Sprint 3 Fase 2. Karena lingkup fase transaksional besar, saya pecah lagi: Fase 2A = Stock Adjustment (dokumen koreksi stok), yang jadi pola untuk Opname (opname menghasilkan adjustment saat completion). Opname & Transfer & Dashboard = Fase 2B berikutnya.

Implementasi mengikuti aturan domain #19-#22:
- **Lifecycle**: DRAFT→SUBMITTED→APPROVED→COMPLETED, plus DRAFT/SUBMITTED→CANCELLED. APPROVED & COMPLETED tidak bisa cancel. Guard transisi via `canTransition` di domain + dicek ulang di repository dengan FOR UPDATE.
- **Stok hanya berubah saat COMPLETED** (rule #20): draft/submit/approve tidak menyentuh stok. Draft hanya menyimpan intent; before/after TIDAK diterima dari client.
- **Completion atomik & concurrency-safe**: satu transaksi SERIALIZABLE — lock header, guard APPROVED→COMPLETED, per item reload batch FOR UPDATE → derive authoritative before/after → negative-stock ban (rule #21) → UPDATE inventory_batches → append inventory_movements ADJUSTMENT_IN/OUT (rule #22) dengan source_document_type=STOCK_ADJUSTMENT (idempotency, rule #5) → simpan snapshot before/after di item → flip COMPLETED. Semua commit bersama atau rollback.
- **MVP scope** (rule #21): adjustment hanya beroperasi pada batch yang sudah ada; tidak membuat batch baru.

Yang dibangun (pola Clean Architecture konsisten):
- Migrasi 1700000000016 (stock_adjustments) & 1700000000017 (stock_adjustment_items).
- Domain: adjustmentStatus (canTransition), adjustmentReason (7 reason + IN/OUT), entities CreateStockAdjustment/UpdateStockAdjustment/StockAdjustment, abstract StockAdjustmentRepository.
- Applications: 7 use case (Create, Update, Submit, Approve, Cancel, Complete, Get list/detail). Use case tipis; Create/Update memverifikasi batch existence + outlet/product match via InventoryRepository.
- Infrastructures: StockAdjustmentRepositoryPostgres (raw SQL, generate ADJ-YYYY-NNNNNN, changeStatus guard, complete atomik) + wiring DI (repo + 7 use case).
- Interfaces: StockAdjustmentController 8 endpoint di /inventory/adjustments dengan permission inventory.adjustment.read/create/update/approve/complete, 3 DTO, module, Swagger tag.
- Error codes + unit test semua layer.
