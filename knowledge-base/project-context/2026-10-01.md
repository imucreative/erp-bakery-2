Yang saya kerjakan: mempelajari modul PR (service, composable, list/form/detail
view, 11 komponen stateless) dan `lib/format.ts`, lalu membangun modul PO yang
setara:

- Service `purchase-order.service.ts`: interface `PurchaseOrder`/`Item`/
  `StatusLog` + payload create/update/approve/reject/cancel + method
  list/getById/create/update/submit/approve/reject/cancel, label status, dan
  `statusBadgeColor`. Field pajak per item (`taxPercent`, `taxAmount`, `total`)
  dan total dokumen (`totalAmount`, `taxTotal`, `grandTotal`) bersifat
  server-authoritative — payload create/update sengaja tidak mengirimnya.
- Composable `usePurchaseOrders.ts`: list state (pagination, debounced search
  by poNumber, filter status + supplier). Error dinormalkan lewat `toMessage`
  yang di-reuse dari `usePurchaseRequests` (menggabungkan fieldErrors).
- Komponen `src/components/procurement/purchase-order/*` + barrel `index.ts`:
  FilterBar (search+status+supplier), Table, HeaderFields, ItemsEditor,
  Summary, ItemsTable, ActionBar, Timeline, ActionModals.
- View `PurchaseOrderList.vue`, `PurchaseOrderForm.vue`, `PurchaseOrderDetail.vue`.
- Router: 4 rute (`/procurement/purchase-orders`, `/new`, `/:id`, `/:id/edit`)
  dengan `/new` sebelum `/:id`; permission po.read/po.create/po.update.
- Sidebar: item "Purchase Orders" di grup Procurement (setelah Purchase Requests).

Keputusan penting:
- **Prefill item dari PR (client-side)**: saat PR sumber dipilih di form create,
  saya fetch detail PR lalu prefill baris item (product/qty/uom dari PR,
  `unitPrice` default dari `estimatedPrice` PR, `taxPercent` default 0) agar user
  bisa meninjau/menyesuaikan harga & pajak sebelum submit — lebih transparan
  daripada mengandalkan prefill backend. Namun bila user mengosongkan semua
  baris, `items` dikirim `undefined` sehingga backend tetap prefill dari PR.
- **Outlet tujuan read-only**: diwarisi dari PR di backend; di form ditampilkan
  read-only (dari detail PR), PR dikunci saat edit.
- **Payment term default vendor**: saat vendor dipilih, bila supplier punya
  `defaultPaymentTermId` dan user belum override, termin otomatis diisi.
- **Preview jatuh tempo**: estimasi due date = orderDate + dueDays termin
  ditampilkan sebagai hint read-only; nilai final tetap dihitung server.
- **Aksi lifecycle**: DRAFT=Edit/Submit/Cancel; SUBMITTED=Approve/Reject(note
  wajib); REJECTED=Edit/Cancel; APPROVED=Cancel (PO boleh APPROVED→CANCELLED);
  CANCELLED=terminal. Reject note wajib divalidasi lokal di modal.
- Semua list lookup memakai `limit: 100` (bukan 200) sesuai batas backend.
