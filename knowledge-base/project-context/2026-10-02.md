## [--:--] Bugfix runtime 500 posting inventory Goods Receipt (ambiguitas tipe $1) — backend-dev

PM mendelegasikan bugfix kecil & terfokus: jalur `POST /api/v1/goods-receipts/:id/complete`
melempar HTTP 500 saat posting inventory, dengan error Postgres asli
`inconsistent types deduced for parameter $1` di
`applyBalanceAndAppendMovement` (helper `inventoryPosting.ts`), dipanggil dari
`GoodsReceiptRepositoryPostgres.complete`. Terjadi di setiap complete GR (termasuk
partial) karena jalur ini selalu dilalui saat posting PURCHASE ke batch.

**Akar masalah.** Pada query UPDATE `inventory_batches`, parameter `$1` dipakai
dua kali dengan konteks tipe berbeda: sebagai nilai kolom `qty_available`
(bertipe `NUMERIC(18,3)`, lihat migrasi `1700000000014_create-table-inventory-batches.js`)
dan sebagai operand perbandingan `$1 = 0` terhadap integer literal. Postgres
tidak bisa mendeduksi satu tipe konsisten untuk `$1` sehingga melempar error.
Bug lolos unit test karena test memakai mock `pg`, bukan Postgres asli, jadi
tidak ada deduksi tipe server-side.

**Perbaikan.** Memberi cast eksplisit `$1::numeric` di kedua pemakaian pada
query UPDATE, sehingga `qty_available = $1::numeric` dan `CASE WHEN $1::numeric = 0 ...`.
Daftar/urutan parameter tidak diubah. Semantik dijaga: inbound re-activate batch
(`$2` → ACTIVE), qty 0 → CONSUMED.

Saya telusuri seluruh backend untuk pola ambiguitas yang sama (`WHEN $1 = 0`
dengan `qty_available = $1`) dan menemukan pola identik di 4 repo lain. Semua
diperbaiki dengan cast eksplisit yang sama:
- `StockAdjustmentRepositoryPostgres.ts` (ADJUSTMENT_IN/OUT)
- `StockOpnameRepositoryPostgres.ts`
- `StockTransferRepositoryPostgres.ts` (update batch sumber)
- `ProductionOrderRepositoryPostgres.ts` (PRODUCTION_CONSUME)

Query `SET qty_available = $1, status = 'ACTIVE'` di StockTransfer (update batch
tujuan) TIDAK diubah karena `$1` di situ hanya dipakai sebagai nilai kolom numeric
tanpa perbandingan, jadi tidak ambigu.

**Verifikasi.**
- `npx tsc --noEmit` di `backend/` → bersih (exit 0).
- `npx jest --runInBand --forceExit` → 143 suites / 1180 tests pass, nol regresi
  (sesuai baseline terakhir).
- Reproduksi terhadap Postgres ASLI: BELUM dapat dijalankan di environment ini.
  Repo tidak punya infrastruktur integration test berbasis DB nyata — tidak ada
  referensi `INVENTORY_INTEGRATION_DATABASE_URL` maupun test hardening inventory
  di `backend/src`. Sesuai instruksi, saya TIDAK membuat DB baru. Cara reproduksi
  manual: jalankan Postgres (mis. `config/database/test.json` →
  `postgresql://postgres:postgres@localhost:5435/erp_bakery_test`) dengan migrasi
  terpasang, lalu panggil `complete` GR (buat batch baru & batch existing) via
  endpoint/pg nyata; sebelum fix query melempar `inconsistent types deduced for
  parameter $1`, sesudah fix berjalan normal.

- File yang diubah:
  - `backend/src/Infrastructures/repository/helpers/inventoryPosting.ts`
  - `backend/src/Infrastructures/repository/StockAdjustmentRepositoryPostgres.ts`

## [--:--] Procurement: CANCELLED bukan soft-delete + endpoint picker sumber outstanding — backend-dev

PM mendelegasikan dua perubahan backend lintas 3 modul procurement (Purchase
Request, Purchase Order, Goods Receipt), dengan larangan tegas: TIDAK mengubah
lifecycle/transisi status (`canTransition` tetap) dan TIDAK menyentuh frontend.
Sebelum menulis kode saya pelajari dulu repo nyata (raw SQL + `pg`, bukan Prisma),
abstract repository, use case list/outstanding, controller, dan pola unit test
(mock `pg` berurutan). Konteks ini dipakai agar perubahan konsisten dengan pola
yang sudah ada.

**Keputusan desain (Opsi A, disetujui user) — CANCELLED ≠ soft-delete.**
Sebelumnya aksi cancel menandai `status='CANCELLED'` SEKALIGUS `deleted_at=NOW()`,
sehingga query list (filter `deleted_at IS NULL`) menyembunyikan dokumen CANCELLED.
Opsi A: CANCELLED adalah status bisnis terminal yang HARUS tetap tampil; `deleted_at`
dikembalikan ke makna "benar-benar dihapus (hard-delete)".

Perubahan tiap repo:
- `PurchaseRequestRepositoryPostgres` & `PurchaseOrderRepositoryPostgres`: parameter
  `softDelete` pada `_transition` DIHAPUS (hanya dipakai oleh cancel; tidak ada
  pemakai lain — sudah diverifikasi via grep). `cancel()` kini transisi biasa ke
  CANCELLED (status + log + updated_by/at) tanpa menulis `deleted_at/deleted_by`.
- `GoodsReceiptRepositoryPostgres.cancel()`: query UPDATE diubah dari
  `SET status='CANCELLED', deleted_at=NOW(), deleted_by=$1` menjadi set status
  CANCELLED + updated_by/at saja. Tetap pakai `canTransition` & `_insertLog`.
- Komentar `getConsumedQtyByPoItem` (GR→PO) & `getConsumedQtyByPrItem` (PO→PR)
  diperbarui: kebenaran pengecualian CANCELLED/REJECTED bersandar pada klausa
  STATUS (`IN ('DRAFT','COMPLETED')` dan `IN ('DRAFT','SUBMITTED','APPROVED')`),
  BUKAN pada `deleted_at`. Komentar lama yang menyesatkan ("CANCELLED which is
  also soft-deleted") sudah dihapus. Guard `deleted_at IS NULL` dipertahankan
  hanya untuk menyaring baris hard-deleted.
- Doc comment abstract repository (cancel) di ketiga domain + ApiOperation cancel
  GR diperbarui agar tidak lagi menyebut "soft-delete".
- Audit: tidak ditemukan tempat lain yang mengandalkan "CANCELLED ⇒ deleted_at
  terisi" untuk kebenaran bisnis; outstanding sudah murni berbasis status.

**Migrasi backfill `1700000000046_backfill-cancelled-not-soft-deleted.js`.**
Mengosongkan `deleted_at/deleted_by` untuk baris `status='CANCELLED' AND
deleted_at IS NOT NULL` di `purchase_requests`, `purchase_orders`,
`goods_receipts`, sehingga dokumen lama yang terlanjur tersembunyi muncul lagi.
Idempoten, company-agnostic (semua tenant), hanya menyentuh baris CANCELLED.
`down` sengaja no-op (diberi komentar): re-apply `deleted_at` akan menyembunyikan
lagi — justru perilaku yang diperbaiki — dan down tidak boleh merusak/menyembunyikan data.

**Endpoint picker "sumber yang masih punya outstanding".** Pendekatan: filter
opsional pada endpoint LIST existing (tanpa mengubah kontrak default yang tetap
menampilkan semua, termasuk habis & CANCELLED), dengan agregasi di DB (anti N+1,
tanpa duplikasi aturan lifecycle):
- `GET /purchase-orders?receivable=true` → hanya PO `APPROVED` yang punya ≥1 item
  dengan outstanding receivable > 0 (outstanding item = qtyPO − Σ(accepted+rejected)
  GR status DRAFT/COMPLETED, not hard-deleted). Dipakai picker pembuatan GR.
  Permission tetap `procurement.po.read` (endpoint list).
- `GET /purchase-requests?orderable=true` → hanya PR `APPROVED` yang punya ≥1 item
  dengan outstanding orderable > 0 (outstanding = qtyPR − Σ qty PO status
  DRAFT/SUBMITTED/APPROVED per product). Dipakai picker pembuatan PO. Permission
  tetap `procurement.pr.read`.
  Filter diwujudkan via `EXISTS (... poi.quantity > COALESCE(SUM(...),0) ...)`.
  Dialirkan: QueryDto (`@IsBooleanString`, controller konversi `=== 'true'`) →
  use case list (`receivable`/`orderable`) → repository filter. Bentuk data yang
  dikembalikan mengikuti list existing (minim perubahan frontend). ApiOperation
  kedua list diperbarui mendokumentasikan flag picker.

**Verifikasi.**
- `npx tsc --noEmit` di `backend/` → bersih (exit 0).
- `npx jest --runInBand --forceExit` → 144 suites / 1188 tests pass (baseline
  143/1180; +1 suite yaitu PurchaseOrderRepositoryPostgres.test.ts, +8 test),
  nol regresi. Test baru: cancel tidak soft-delete (PR/PO/GR, dokumen CANCELLED
  tetap muncul & tetap menulis log), picker hanya kembalikan APPROVED + outstanding>0,

- Migrasi backfill: di-apply ke DB test (`config/database/test.json`) → sukses
  (ketiga UPDATE jalan, tercatat di pgmigrations); `migrate:test:down` lalu re-up
