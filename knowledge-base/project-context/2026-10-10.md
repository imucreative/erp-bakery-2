### Aturan disable final yang diterapkan di `ProductGrid.vue`

| Kondisi | Perilaku | Badge |
|---|---|---|
| `availableQty > 0` | aktif | "Stok: N" (hijau) |
| `availableQty === 0 && expiredQty > 0` | **disabled** | "Kedaluwarsa — tidak bisa dijual" (merah, `Badge color="error"`) |
| `availableQty === 0 && expiredQty === 0` | **disabled** | "Stok habis" (netral, `Badge color="light"`) |
| `saleMode === 'MADE_TO_ORDER' && hasToppings` | **TETAP AKTIF** bahkan `availableQty === 0` | "Bisa ditambah topping" (`info`) |

Pengecualian topping diterapkan sebagai pengecualian desain yang disengaja (topped line selalu dibuat fresh dari resep), implemented via `acceptsToppings()` → `isSellable()`. Disabled ditegakkan di **dua lapis**: atribut native `disabled` + `aria-disabled` pada `<button>` (dengan styling `disabled:*` termasuk dark mode), **dan** guard `if (!isSellable(product)) return` di `onCardClick` sebagai pengaman jalur keyboard/programmatik. Kartu disabled tidak punya ikon `Plus` hover (sudah `v-if="card.sellable"`), dan `title` berisi alasannya.

### Keputusan penting: badge sale-mode dihapus dari grid

Brief memberi peringatan tegas: `saleMode` di response API adalah **kemampuan** (punya resep aktif → panel modifier topping bisa dibuka), BUKAN mode penjualan yang dipakai checkout — dan "lebih baik tidak menampilkan sama sekali daripada menyesatkan kasir". Badge lama `SALE_MODE_LABELS[saleMode]` ("Jual Stok" / "Buat Sesuai Pesanan") justru menyiratkan mode jual, jadi **saya hapus dari grid** dan ganti dengan badge kapabilitas netral "Bisa ditambah topping" yang hanya muncul untuk produk yang benar-benar menerima topping. Konsekuensi: grid kini menampilkan fakta yang acted-upon kasir (apakah ada stok sellable, apakah bisa topping) bukan asumsi mode. `SALE_MODE_LABELS` + `saleModeBadgeColor` tetap diekspor di service karena masih dipakai `SalesOrderItemsTable.vue` — jadi tidak ada dead export. **Kalau user justru masih ingin melihat mode di grid, tinggal bilang; perubahanya 3 baris.**

### §3 — error checkout: sebelum vs sesudah

**Sebelum:** `onConfirmPayment` catch → `payError.value = toMessage(error)` → tampil di `PaymentDrawer` (`errorMessage` prop) sebagai alert merah. Cart **sudah tidak terhapus** (behavior ini sudah benar — `cart.clear()` hanya di `onReceiptDone` / `onOutletChange` / `onCloseShiftDone`), tapi pesannya mentah dari backend dan belum memberi tahu kasir apa yang harus dilakukan.

**Sesudah:** mekanisme display **tidak berubah** (tetap `payError` → PaymentDrawer alert yang sudah ada; tidak ada mekanisme baru). Yang berubah adalah isi pesannya lewat `toCheckoutError(error)`: untuk dua stock rejection, pesan backend asli + hint kasir yang menyebut jalan keluar yang benar. Karena `AllExceptionsFilter` tidak mengirim kode domain, pencocokan dilakukan terhadap string persis hasil `DomainErrorTranslator` (`startsWith`), dengan fallback aman: error lain (`TOPPING.NOT_ALLOWED`, `PAYMENT.AMOUNT_MISMATCH`, dll) tetap lewat `toMessage` apa adanya. `isStockRejection` juga dipakai untuk trigger `loadProducts()` supaya badge grid mencerminkan availability server terbaru setelah penolakan. Cart tetap utuh — kasir bisa turunkan qty / hapus baris / retry.

## [16:20] Topping ikut stock-first + otorisasi outlet POS grid + koreksi JSDoc mode — backend-dev

PM mendelegasikan 3 perbaikan backend atas 4 temuan MEDIUM dari QA (13:45). Dua di antaranya menutup bug yang dilaporkan user: penjualan POS bertopping **tidak pernah mengurangi stock waffle hasil produksi**, malah memotong bahan baku/resep. Akar masalahnya ada di dua tempat yang sama-sama mengunci topping ke mode `MADE_TO_ORDER` saja, sehingga jalur backflush "melolos" dan stok jadi di-skip.

### Paket 1 — Topping ikut stock-first (akar masalah, bukan perluasan)

Tiga perubahan di `SalesOrderRepositoryPostgres.ts`:

1. **`resolveCheckoutItems`** — early-branch "topped line selalu fresh / skip query stok" **dihapus**. Sekarang semua lini (bertopping atau tidak) melewati **satu** query stok yang sama dengan dua SUM (`sellable_qty` / `expired_qty`, tetap dua-duanya di-guard `qty_available > 0` + `status = 'ACTIVE'`). Kolom `product_type` ikut dilepas dari SELECT produk karena tidak lagi dipakai untuk cabang mode.
2. **Guard topping** — `saleMode !== 'MADE_TO_ORDER' || !product.has_toppings` menjadi **`req.toppings.length > 0 && !product.has_toppings`**. Topping kini diizinkan pada mode apa pun; satu-satunya gate produk adalah flag `has_toppings`.
3. **`pay()`** — **konsumsi topping dipindahkan keluar percabangan mode**, tepat sebelum loop `_consumeFefo`. Jadi topping dipotong pada kedua mode, tetap `qty_per_item × item.qty` per topping terpilih. Branch `MADE_TO_ORDER` (backflush resep) dan `STOCK` (produk jadi) tidak berubah isinya.

Kolom `recipe_id` **tidak dihapus** dari skema: resolver selalu menulis `null` sekarang, tapi `pay()` tetap harus bisa membaca order lama yang sudah tersimpan `MADE_TO_ORDER`, dan `refund()` mem-balikkannya. Tidak ada migrasi DB (CHECK constraint `sale_mode IN ('MADE_TO_ORDER','STOCK')` sudah menerima keduanya).

**Aturan resolver final (satu aturan seragam, tanpa cabang topping):**

| Kasus | saleMode | Yang dipotong saat `pay()` |
|---|---|---|
| stok sellable ≥ qty | `STOCK` | produk jadi + topping (bila ada) |
| stok sellable < qty, ada yang expired | ditolak | — (`SALES_ORDER.STOCK_EXPIRED`) |
| stok 0 / tidak cukup & tidak ada expired | ditolak | — (`INVENTORY.INSUFFICIENT_STOCK`) |

Konsekuensi yang disadari dan diterima: **berkas topping tidak pernah(screen) auto-backflush lagi** — stok waffle habis berarti penjualan bertopping juga ditolak, kasir harus membuat Production Order lebih dulu. Ini konsisten dengan keputusan beku "POS tidak auto-backflush".
