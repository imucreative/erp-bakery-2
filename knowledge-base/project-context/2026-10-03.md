## [Opsi X] Recipe (BOM) delete: ARCHIVED kini dapat dihapus — backend-dev

User memutuskan Opsi X: aturan HAPUS (soft-delete) resep dilonggarkan. Sebelumnya
`softDelete` hanya mengizinkan status DRAFT. Sekarang DRAFT **dan** ARCHIVED boleh
dihapus (soft-delete) agar arsip lama yang menumpuk bisa dibersihkan. Hanya status
ACTIVE yang TIDAK boleh dihapus karena sedang dipakai. Ini soal menghapus arsip,
bukan menghidupkan arsip — model B2 (ARCHIVED terminal, revisi via duplikat-ke-draft)
TETAP, dan ini tetap soft-delete (deleted_at di-set, data retained, hidden dari reads),
bukan transisi status (recipeStatus.ts tidak disentuh).

Yang dikerjakan:
- `RecipeRepositoryPostgres.softDelete`: validasi diubah — tolak hanya status ACTIVE
  dengan InvariantError **`RECIPE.ACTIVE_NOT_DELETABLE`** (menggantikan
  `RECIPE.ONLY_DRAFT_DELETABLE`). SELECT FOR UPDATE company-scoped + deleted_at IS NULL,
  404 RECIPE.NOT_FOUND bila tak ada, lalu set deleted_at=NOW(), updated_at=NOW() tetap.
- Doc comment abstract `RecipeRepository.softDelete` diperbarui (DRAFT & ARCHIVED dapat
  dihapus; ACTIVE tidak).
- Swagger DELETE di `recipe.controller.ts`: @ApiOperation "soft-delete DRAFT or ARCHIVED
  (not ACTIVE)", @ApiResponse 400 jadi "Recipe is ACTIVE (ACTIVE recipes cannot be deleted)",
  header-comment route diperbarui.
- Test repo: tambah kasus sukses ARCHIVED, pertahankan sukses DRAFT, ubah kasus ACTIVE
  jadi ditolak (ACTIVE_NOT_DELETABLE), 404 tetap. Test use case: assertion propagasi error
  diubah ke RECIPE.ACTIVE_NOT_DELETABLE.
- KB: `28.production-domain.md` section 5a diperbarui (diagram + narasi: DRAFT & ARCHIVED
  deletable, ACTIVE tidak; tetap soft-delete; model B2 tetap).

- File yang diubah:

## [Producible Qty] Endpoint kapasitas produksi (GET /production/producible) — backend-dev

User (branch feature/production) meminta endpoint READ-ONLY untuk Form Produksi:
saat user memilih PRODUK JADI + OUTLET, frontend perlu menampilkan resep ACTIVE,
MAKS qty produk jadi yang bisa diproduksi dari stok bahan di outlet itu, dan daftar
bahan (kebutuhan per unit, stok tersedia, mana yang membatasi). Perhitungan WAJIB di
backend sebagai satu sumber kebenaran, dan harus KONSISTEN dengan backflushing jalur
produksi instan (createInstant). Lifecycle instant-complete TIDAK diubah; tidak commit.

Yang dikerjakan:
- Ekstrak **helper konsumsi bersama** `Domains/production/productionConsumption.ts`:
  `scaledIngredientConsumption(base, loss, scaleFactor) = base*scale*(1+loss/100)` dan
  `ingredientRequirementPerUnit(base, loss, yieldQty) = scaledIngredientConsumption(base, loss, 1/yieldQty)`.
  Ini jadi SATU-SATUNYA tempat rumus konsumsi. `createInstant` di
  ProductionOrderRepositoryPostgres di-refactor memakai `scaledIngredientConsumption`
  (menggantikan ekspresi inline) → preview = eksekusi dijamin oleh rumus yang sama.
- Repository: tambah `ProductionOrderRepository.getProducible(companyId, productId, outletId)`
  + impl Postgres. Resolve resep ACTIVE produk (404 RECIPE.NO_ACTIVE_RECIPE bila tak ada),
  ambil recipe_items (qty, loss_percentage, uom_id), hitung `requiredPerUnit` via helper,
  ambil stok bahan = SUM(qty_available) inventory_batches ACTIVE per product di outlet
  (sumber kebenaran sama dgn Stock On Hand, rule #8), `maxUnits = floor(available/perUnit)`,
  `producibleQty = MIN(maxUnits)` lintas bahan; tandai isLimiting pada bahan di MIN.
  Edge: requiredPerUnit 0 → tak membatasi (maxUnits unbounded, skip MIN); stok 0 → 0;
  resep kosong → 0. Pembulatan floor ke unit bulat (output produksi bilangan bulat) —
  diasumsikan & didokumentasikan; createInstant sendiri menerima qty kontinu (over/under-yield),
  tapi preview adalah planning sehingga floor-integer adalah jawaban konservatif yang benar.
