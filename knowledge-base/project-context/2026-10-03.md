## [Opsi X] Recipe (BOM) delete: ARCHIVED kini dapat dihapus — backend-dev

User memutuskan Opsi X: aturan HAPUS (soft-delete) resep dilonggarkan. Sebelumnya
`softDelete` hanya mengizinkan status DRAFT. Sekarang DRAFT **dan** ARCHIVED boleh
dihapus (soft-delete) agar arsip lama yang menumpuk bisa dibersihkan. Hanya status
ACTIVE yang TIDAK boleh dihapus karena sedang dipakai. Ini soal menghapus arsip,
bukan menghidupkan arsip — model B2 (ARCHIVED terminal, revisi via duplikat-ke-draft)
TETAP, dan ini tetap soft-delete (deleted_at di-set, data retained, hidden dari reads),
bukan transisi status (recipeStatus.ts tidak disentuh).

Yang dikerjakan:
- `RecipeRepositoryPostgres.softDelete`: validasi diubah — tolak hanya status ACTIVE
  dengan InvariantError **`RECIPE.ACTIVE_NOT_DELETABLE`** (menggantikan
  `RECIPE.ONLY_DRAFT_DELETABLE`). SELECT FOR UPDATE company-scoped + deleted_at IS NULL,
  404 RECIPE.NOT_FOUND bila tak ada, lalu set deleted_at=NOW(), updated_at=NOW() tetap.
- Doc comment abstract `RecipeRepository.softDelete` diperbarui (DRAFT & ARCHIVED dapat
  dihapus; ACTIVE tidak).
- Swagger DELETE di `recipe.controller.ts`: @ApiOperation "soft-delete DRAFT or ARCHIVED
  (not ACTIVE)", @ApiResponse 400 jadi "Recipe is ACTIVE (ACTIVE recipes cannot be deleted)",
  header-comment route diperbarui.
- Test repo: tambah kasus sukses ARCHIVED, pertahankan sukses DRAFT, ubah kasus ACTIVE
  jadi ditolak (ACTIVE_NOT_DELETABLE), 404 tetap. Test use case: assertion propagasi error
  diubah ke RECIPE.ACTIVE_NOT_DELETABLE.
- KB: `28.production-domain.md` section 5a diperbarui (diagram + narasi: DRAFT & ARCHIVED
  deletable, ACTIVE tidak; tetap soft-delete; model B2 tetap).

- File yang diubah:

## [Producible Qty] Endpoint kapasitas produksi (GET /production/producible) — backend-dev

User (branch feature/production) meminta endpoint READ-ONLY untuk Form Produksi:
saat user memilih PRODUK JADI + OUTLET, frontend perlu menampilkan resep ACTIVE,
MAKS qty produk jadi yang bisa diproduksi dari stok bahan di outlet itu, dan daftar
bahan (kebutuhan per unit, stok tersedia, mana yang membatasi). Perhitungan WAJIB di
backend sebagai satu sumber kebenaran, dan harus KONSISTEN dengan backflushing jalur
produksi instan (createInstant). Lifecycle instant-complete TIDAK diubah; tidak commit.

Yang dikerjakan:
- Ekstrak **helper konsumsi bersama** `Domains/production/productionConsumption.ts`:
  `scaledIngredientConsumption(base, loss, scaleFactor) = base*scale*(1+loss/100)` dan
  `ingredientRequirementPerUnit(base, loss, yieldQty) = scaledIngredientConsumption(base, loss, 1/yieldQty)`.
  Ini jadi SATU-SATUNYA tempat rumus konsumsi. `createInstant` di
  ProductionOrderRepositoryPostgres di-refactor memakai `scaledIngredientConsumption`
  (menggantikan ekspresi inline) → preview = eksekusi dijamin oleh rumus yang sama.
- Repository: tambah `ProductionOrderRepository.getProducible(companyId, productId, outletId)`
  + impl Postgres. Resolve resep ACTIVE produk (404 RECIPE.NO_ACTIVE_RECIPE bila tak ada),
  ambil recipe_items (qty, loss_percentage, uom_id), hitung `requiredPerUnit` via helper,
  ambil stok bahan = SUM(qty_available) inventory_batches ACTIVE per product di outlet
  (sumber kebenaran sama dgn Stock On Hand, rule #8), `maxUnits = floor(available/perUnit)`,
  `producibleQty = MIN(maxUnits)` lintas bahan; tandai isLimiting pada bahan di MIN.
  Edge: requiredPerUnit 0 → tak membatasi (maxUnits unbounded, skip MIN); stok 0 → 0;
  resep kosong → 0. Pembulatan floor ke unit bulat (output produksi bilangan bulat) —
  diasumsikan & didokumentasikan; createInstant sendiri menerima qty kontinu (over/under-yield),
  tapi preview adalah planning sehingga floor-integer adalah jawaban konservatif yang benar.

## [Fix] Stock Transfer receive gagal — INVENTORY.DUPLICATE_MOVEMENT_SOURCE — backend-dev

User melaporkan bug backend di branch `feature/stock-transfer`: aksi `receive`

WHERE source_document_type/id NOT NULL — index TIDAK menyertakan `movement_type`.

Di `StockTransferRepositoryPostgres`, `dispatch()` meng-INSERT movement
`TRANSFER_OUT` dengan source key `(STOCK_TRANSFER, transferId, item.id)` dan
allocation NULL; `receive()` meng-INSERT `TRANSFER_IN` dengan source key IDENTIK
kecuali `movement_type`. Karena index mengabaikan `movement_type`, baris
TRANSFER_IN bentrok dengan TRANSFER_OUT yang sudah ada (Postgres 23505) dan
di-mapping repo menjadi `INVENTORY.DUPLICATE_MOVEMENT_SOURCE`. Ini juga menyimpang
dari knowledge-base doc 35 §8 yang mewajibkan idempotency per source allocation
**dan movement type**.

yang DROP index lama lalu CREATE ULANG dengan nama SAMA

sebagai kolom key PERTAMA, mempertahankan COALESCE untuk item_id & allocation_id
dan klausa WHERE yang sama. `exports.down` mengembalikan index ke bentuk lama
(tanpa movement_type). Nama index dipertahankan agar repo (yang memetakan 23505 ke
`INVENTORY.DUPLICATE_MOVEMENT_SOURCE`) tidak perlu diubah. Logika repository
dispatch/receive TIDAK diubah (keduanya sudah benar: Serializable + rollback penuh
saat gagal).

Test: menambah 2 test mock-based di `StockTransferRepositoryPostgres.test.ts`
(repo belum punya infra DB-backed integration test — semua test repo berbasis mock
`pg`): (1) regression "dispatch → receive sukses" yang memverifikasi INSERT movement
pada dispatch pakai `TRANSFER_OUT` dan pada receive pakai `TRANSFER_IN` serta kedua
transisi selesai (IN_TRANSIT lalu COMPLETED) tanpa bentrok; (2) replay/duplicate
pada receive tetap dipetakan ke `INVENTORY.DUPLICATE_MOVEMENT_SOURCE` saat 23505 +

movement_type (replay OUT atau replay IN yang sama tetap ditolak).

  dijumlah dari purchase_return_items per status, keyed by goods_receipt_item_id).
  `postedAccepted = movement.qty`, `sourceBatchId = movement.batch_id`,
  `sourceMovementId = movement.id`. GR wajib COMPLETED (else
  `PURCHASE_RETURN.GOODS_RECEIPT_NOT_COMPLETED`).
- **Reservasi (rule #18):** DRAFT tidak mereservasi; SUBMITTED mereservasi (hanya status
  flip + validasi returnable); CANCELLED melepas (status pindah dari SUBMITTED membuat
  return ini tak lagi dihitung di submitted-sum); COMPLETED meng-konsumsi (posting RETURN).
  returnable derivation selalu dihitung ulang authoritative saat submit (EXCLUDE return
  ini dari submitted-sum agar tidak menghitung diri sendiri).
- **Source key reversal RETURN (rule #16/#19, doc 35 §8):** movement `RETURN` (OUT) ditulis
  dengan `source_document_type='PURCHASE_RETURN'`, `source_document_id=returnId`,
  `source_document_item_id=returnItemId`, `source_document_allocation_id=sourceBatchId`.
  Unik per (return, return item, batch); 23505 → `INVENTORY.DUPLICATE_MOVEMENT_SOURCE`
  via helper `translateDuplicateSourceKey`. Karena movement_type kini bagian index unik
  (migrasi 049), RETURN tak bertabrakan dengan PURCHASE GR.
- **Completion (rule #19) ATOMIC SERIALIZABLE:** lock header FOR UPDATE → idempoten bila
  sudah COMPLETED (no-op sukses, DB index jadi guard akhir) → per item reload batch asal
  FOR UPDATE, derive before/after → **bila batch < qty retur TOLAK
  `INVENTORY.INSUFFICIENT_STOCK`** (disetujui user; barang sudah keluar) → kurangi
  qty_available (CONSUMED bila 0) → INSERT movement RETURN → flip COMPLETED + audit +
  status log → COMMIT. Posting manual (bukan helper `applyBalanceAndAppendMovement`) agar
  mengikuti pola Stock Transfer OUT (negatif stok = INSUFFICIENT, bukan auto-create batch).
- **Numbering:** `RTN-YYYY-XXXXXX` (doc 35 §2), race-safe via MAX(serial) dalam transaksi +
  partial unique index `WHERE deleted_at IS NULL`.
- **Soft-delete/cancel:** ikut pola GR Opsi A — CANCELLED terminal, tetap VISIBLE, TIDAK
  men-set deleted_at (deleted_at hanya untuk hard-delete). Dikonfirmasi dari GR cancel.
- **Reason (rule #17):** controlled `DAMAGED/WRONG_ITEM/QUALITY_ISSUE/EXPIRED/OVER_DELIVERY/
  OTHER`; `reasonDescription` WAJIB bila OTHER — divalidasi di DTO (class-validator) &

- **Company-scope penuh** di semua query; snapshot supplier (id+code+name) & outlet
  (id+code+name) diwarisi dari GR (via supplierId & destinationOutletId GR), bukan input user.
