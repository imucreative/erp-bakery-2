## [Opsi X] Recipe (BOM) delete: ARCHIVED kini dapat dihapus — backend-dev

User memutuskan Opsi X: aturan HAPUS (soft-delete) resep dilonggarkan. Sebelumnya
`softDelete` hanya mengizinkan status DRAFT. Sekarang DRAFT **dan** ARCHIVED boleh
dihapus (soft-delete) agar arsip lama yang menumpuk bisa dibersihkan. Hanya status
ACTIVE yang TIDAK boleh dihapus karena sedang dipakai. Ini soal menghapus arsip,
bukan menghidupkan arsip — model B2 (ARCHIVED terminal, revisi via duplikat-ke-draft)
TETAP, dan ini tetap soft-delete (deleted_at di-set, data retained, hidden dari reads),
bukan transisi status (recipeStatus.ts tidak disentuh).

Yang dikerjakan:
- `RecipeRepositoryPostgres.softDelete`: validasi diubah — tolak hanya status ACTIVE
  dengan InvariantError **`RECIPE.ACTIVE_NOT_DELETABLE`** (menggantikan
  `RECIPE.ONLY_DRAFT_DELETABLE`). SELECT FOR UPDATE company-scoped + deleted_at IS NULL,
  404 RECIPE.NOT_FOUND bila tak ada, lalu set deleted_at=NOW(), updated_at=NOW() tetap.
- Doc comment abstract `RecipeRepository.softDelete` diperbarui (DRAFT & ARCHIVED dapat
  dihapus; ACTIVE tidak).
- Swagger DELETE di `recipe.controller.ts`: @ApiOperation "soft-delete DRAFT or ARCHIVED
  (not ACTIVE)", @ApiResponse 400 jadi "Recipe is ACTIVE (ACTIVE recipes cannot be deleted)",
  header-comment route diperbarui.
- Test repo: tambah kasus sukses ARCHIVED, pertahankan sukses DRAFT, ubah kasus ACTIVE
  jadi ditolak (ACTIVE_NOT_DELETABLE), 404 tetap. Test use case: assertion propagasi error
  diubah ke RECIPE.ACTIVE_NOT_DELETABLE.
- KB: `28.production-domain.md` section 5a diperbarui (diagram + narasi: DRAFT & ARCHIVED
  deletable, ACTIVE tidak; tetap soft-delete; model B2 tetap).

- File yang diubah:

  - backend/src/Domains/recipes/RecipeRepository.ts
  - backend/src/Interfaces/http/api/recipes/recipe.controller.ts
  - backend/src/Infrastructures/repository/_test/RecipeRepositoryPostgres.test.ts
  - backend/src/Applications/use_case/recipes/_test/RecipeUseCases.test.ts
  - knowledge-base/28.production-domain.md
- Hasil verifikasi: `npx tsc --noEmit` bersih (0 error); `npx jest --runInBand --forceExit`
  144 suites / 1195 tests pass (tanpa regresi).

## [Production Order] Lifecycle disederhanakan jadi INSTANT-COMPLETE + endpoint accessible-outlets — backend-dev

User (branch feature/production) memutuskan menyederhanakan modul Production Order
dari dokumen multi-step (SCHEDULED→IN_PROGRESS→YIELD_COMPLETED→QA_PASSED|QA_FAILED→
COMPLETED, +CANCELLED, dengan endpoint start/yield/qa/complete/cancel) menjadi
"produksi instan" (keputusan 1b, opsi A): membuat production order = LANGSUNG
COMPLETED dalam satu aksi atomic, dengan backflushing seketika. QA dihapus total.
Pencatatan target(scheduledQty)/actual(actualQty)/waste(wasteQty) TETAP dipertahankan.

BAGIAN 1 — Instant-complete:
- `productionStatus.ts`: status diringkas jadi SATU status `COMPLETED` (terminal).
  Buang SCHEDULED/IN_PROGRESS/YIELD_COMPLETED/QA_PASSED/QA_FAILED/CANCELLED. Hapus
  `canTransition` (tak ada transisi lagi); sisakan `isProductionStatus` &
  `isTerminalStatus`. Keputusan: CANCELLED DIBUANG — produksi instan tak punya state
  antara, create either fully-success→COMPLETED atau gagal→rollback total, jadi tak
  ada order in-flight yang bisa dibatalkan.
- `CreateProductionOrder` entity: tambah field actualQty(>=0, wajib), wasteQty(>=0,
  default 0), resultExpiredDate (wajib bila actualQty>0). Validasi minimal sesuai
  arahan user: non-negatif + tipe benar; TIDAK memaksa scheduledQty>=actualQty+wasteQty
  (over/under-yield sah). Kode error baru: ACTUAL_QTY_NOT_MEET_DATA_TYPE_SPECIFICATION,
  ACTUAL_QTY_NEGATIVE, WASTE_INVALID, RESULT_EXPIRY_REQUIRED, RESULT_EXPIRY_INVALID.
- Repository: `schedule` + `complete` DIGABUNG jadi SATU method `createInstant`
  (SERIALIZABLE): resolve resep ACTIVE (recipeId eksplisit atau productId→ACTIVE,
  error RECIPE.NO_ACTIVE_RECIPE), hitung scaleFactor, INSERT header langsung
  status=COMPLETED, backflush bahan FEFO (PRODUCTION_CONSUME, ban stok negatif →
  INVENTORY.INSUFFICIENT_STOCK), bila actualQty>0 buat batch produk jadi
  (PRODUCTION_RESULT) + link result_batch_id, simpan materials[]/results[].
  Hapus start/recordYield/qaPass/qaFail/complete/cancel dari repo & abstract interface.
- Use case: hapus Start/RecordYield/QaCheck/Complete/Cancel ProductionOrderUseCase.
  `CreateProductionOrderUseCase` kini memanggil `createInstant` (tetap validasi outlet
  dulu via OutletRepository.getOutletById). Hapus registrasi use case terkait di
  InfrastructureModule (providers + exports + import).
- Controller: sisakan GET list, GET :id, POST create (=produksi instan). Hapus
  endpoint start/yield/qa/complete/cancel. Hapus DTO record-yield/qa-check/cancel.
  Update create DTO (actualQty/wasteQty/resultExpiredDate) + query DTO status desc.
- Entity ProductionOrder: field `qaNotes` DIBUANG dari entity (tak lagi dibaca/ditulis).
  Kolom DB `qa_notes` DIBIARKAN ada (tak ada migrasi drop) — hanya tak dipakai.
  CHECK constraint status di DB masih superset (COMPLETED termasuk) → tak perlu migrasi.

BAGIAN 2 — Endpoint accessible-outlets:
- `GET /api/v1/outlets/accessible` di OutletController, **JWT-only tanpa
  @RequirePermission** (keputusan: kasir/produksi mungkin tak punya outlet.read).
  Didaftarkan SEBELUM GET :id agar tak bentrok route. OWNER/super-admin → semua outlet
  non-deleted di company aktif; user biasa → hanya user_outlets (is_active) non-deleted.
  Company-scoped, userId dari user.sub, allOutlets = isSuperAdmin || roleCode==='OWNER'.
- Repo: tambah `OutletRepository.findAccessibleByUser(userId, companyId, allOutlets)`
  + implementasi Postgres (branch all-outlets vs JOIN user_outlets). Tambah ke abstract
  contract test.
