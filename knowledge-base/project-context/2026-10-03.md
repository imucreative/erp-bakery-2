## [Opsi X] Recipe (BOM) delete: ARCHIVED kini dapat dihapus — backend-dev

User memutuskan Opsi X: aturan HAPUS (soft-delete) resep dilonggarkan. Sebelumnya
`softDelete` hanya mengizinkan status DRAFT. Sekarang DRAFT **dan** ARCHIVED boleh
dihapus (soft-delete) agar arsip lama yang menumpuk bisa dibersihkan. Hanya status
ACTIVE yang TIDAK boleh dihapus karena sedang dipakai. Ini soal menghapus arsip,
bukan menghidupkan arsip — model B2 (ARCHIVED terminal, revisi via duplikat-ke-draft)
TETAP, dan ini tetap soft-delete (deleted_at di-set, data retained, hidden dari reads),
bukan transisi status (recipeStatus.ts tidak disentuh).

Yang dikerjakan:
- `RecipeRepositoryPostgres.softDelete`: validasi diubah — tolak hanya status ACTIVE
  dengan InvariantError **`RECIPE.ACTIVE_NOT_DELETABLE`** (menggantikan
  `RECIPE.ONLY_DRAFT_DELETABLE`). SELECT FOR UPDATE company-scoped + deleted_at IS NULL,
  404 RECIPE.NOT_FOUND bila tak ada, lalu set deleted_at=NOW(), updated_at=NOW() tetap.
- Doc comment abstract `RecipeRepository.softDelete` diperbarui (DRAFT & ARCHIVED dapat
  dihapus; ACTIVE tidak).
- Swagger DELETE di `recipe.controller.ts`: @ApiOperation "soft-delete DRAFT or ARCHIVED
  (not ACTIVE)", @ApiResponse 400 jadi "Recipe is ACTIVE (ACTIVE recipes cannot be deleted)",
  header-comment route diperbarui.
- Test repo: tambah kasus sukses ARCHIVED, pertahankan sukses DRAFT, ubah kasus ACTIVE
  jadi ditolak (ACTIVE_NOT_DELETABLE), 404 tetap. Test use case: assertion propagasi error
  diubah ke RECIPE.ACTIVE_NOT_DELETABLE.
- KB: `28.production-domain.md` section 5a diperbarui (diagram + narasi: DRAFT & ARCHIVED
  deletable, ACTIVE tidak; tetap soft-delete; model B2 tetap).

- File yang diubah:
  - backend/src/Infrastructures/repository/RecipeRepositoryPostgres.ts
  - backend/src/Domains/recipes/RecipeRepository.ts
  - backend/src/Interfaces/http/api/recipes/recipe.controller.ts
  - backend/src/Infrastructures/repository/_test/RecipeRepositoryPostgres.test.ts
  - backend/src/Applications/use_case/recipes/_test/RecipeUseCases.test.ts
  - knowledge-base/28.production-domain.md
- Hasil verifikasi: `npx tsc --noEmit` bersih (0 error); `npx jest --runInBand --forceExit`
  144 suites / 1195 tests pass (tanpa regresi).
- Keputusan penting: kode error final kasus ACTIVE = `RECIPE.ACTIVE_NOT_DELETABLE`
  (InvariantError). recipeStatus.ts tidak diubah; tidak ada commit.
- Langkah berikutnya: QA verification bila diperlukan; frontend belum disentuh.

## [Recipe UI] Tombol Hapus kini tampil untuk DRAFT & ARCHIVED (Opsi X) — frontend-dev

User meminta penyesuaian kecil pada modul Recipe UI (branch feature/recipe) menindaklanjuti
perubahan backend yang sudah terverifikasi: resep ARCHIVED kini JUGA boleh di-soft-delete,
selain DRAFT; hanya ACTIVE yang ditolak backend dengan 400 RECIPE.ACTIVE_NOT_DELETABLE.

Yang saya kerjakan di frontend-tailadmin:
- Mengubah computed `showDelete` di `RecipeDetail.vue` dari `canManage && status === 'DRAFT'`
  menjadi `canManage && (status === 'DRAFT' || status === 'ARCHIVED')`. Action bar sepenuhnya
  digerakkan oleh prop `show-delete`, jadi tidak ada perubahan logika di `RecipeActionBar.vue`
  selain memperbarui komentar dokumentasi. ARCHIVED kini menampilkan "Duplikat ke Draft" DAN
  "Hapus" berdampingan; tata letak action bar (`flex flex-wrap justify-end gap-3`) tetap rapi.
- Memperbarui teks modal konfirmasi hapus di `RecipeActionModals.vue` agar wajar untuk kedua
  status: deskripsi tidak lagi menyebut "Hanya resep Draft", melainkan "Resep berstatus Draft
  atau Arsip dapat dihapus; resep Aktif tidak dapat dihapus". Warning text juga digeneralkan.
- Memperbarui komentar header lifecycle di ketiga file agar akurat. Handler delete & redirect
  (ke daftar dengan query deleted=1) tetap bekerja untuk kedua status; surface error di modal
  tetap ada sebagai pengaman bila ACTIVE tertembak.

- File yang diubah:
  - frontend-tailadmin/src/views/Production/RecipeDetail.vue (computed showDelete + komentar)
  - frontend-tailadmin/src/components/production/recipe/RecipeActionModals.vue (teks + komentar)
  - frontend-tailadmin/src/components/production/recipe/RecipeActionBar.vue (komentar saja)
- Hasil verifikasi: `npm --prefix frontend-tailadmin run build` HIJAU (vue-tsc + vite, exit 0, built in ~19s).
- Keputusan penting: mengikuti Opsi X user — DRAFT & ARCHIVED deletable, ACTIVE tidak.

## [Production Order UI] Modul dokumen Production Order di frontend-tailadmin — frontend-dev

User meminta membangun UI dokumen "Production Order" di `frontend-tailadmin/`
(stack final: Vue 3 + Vite + Tailwind v4, bukan React) — konversi bahan baku jadi
barang jadi via resep (BOM) dengan lifecycle multi-step + QA. Backend sudah matang;
tidak disentuh, tidak ada commit. Pola ditiru dari modul dokumen termatang
(Stock Adjustment) agar konsisten dengan AGENTS.md doc 48 §2 & frontend-constitution
(doc 19).

Verifikasi kontrak backend dari sumber sebelum menulis:
- `production-order.controller.ts` (base `/production/orders`), guard read=`production-order.read`,
  semua tulis=`production-order.manage`.
- `ProductionOrder` entity: header + `materials[]` + `results[]`.
- PENTING: `ProductionOrderRepositoryPostgres.list()` mengembalikan HEADER SAJA
  (komentar "List returns headers only (materials/results loaded on detail)");
  `materials`/`results` baru terisi saat `getById`/mutasi. Maka tabel list TIDAK
  memakai count materials/results — menampilkan `scheduledQty` di kolom Qty Rencana.
- Lifecycle (productionStatus.ts canTransition): SCHEDULED→(IN_PROGRESS|CANCELLED);
  IN_PROGRESS→YIELD_COMPLETED; YIELD_COMPLETED→(QA_PASSED|QA_FAILED); QA_PASSED→COMPLETED;
  QA_FAILED→COMPLETED; COMPLETED & CANCELLED terminal. DTO yield wajib
  actualQty>0 + resultExpiredDate; qa wajib boolean passed; cancel reason opsional;
  create: productId ATAU recipeId (recipe menang) + scheduledQty>0.

Keputusan desain (ikut instruksi user):
1. Form create: user pilih PRODUK JADI → kirim `productId` saja (bukan recipeId);
   backend resolve resep ACTIVE. Picker produk DIFILTER ke produk yang punya resep
   ACTIVE (ambil recipe list status=ACTIVE, bangun Map productId→label resep), lalu
   tampilkan nama resep ter-resolve sebagai info read-only di bawah picker. Bila tak
   ada produk ber-resep aktif, tampilkan warning & disable tombol submit. Error backend
   (mis. produk tanpa resep aktif) tetap tersurface di halaman.
2. Yield & QA sebagai MODAL (bukan halaman): modal yield (actualQty/wasteQty/
   resultExpiredDate/notes dgn validasi lokal), modal QA (select Lulus/Gagal + qaNotes),
   Start & Complete konfirmasi, Cancel konfirmasi + reason.
3. SKIP preview kebutuhan bahan (MVP) — Materials & Results hanya tampil di detail
   setelah COMPLETED; kalau kosong tampilkan empty state. TANPA timeline (tak ada status log).
   TANPA edit (backend tak punya PUT order).

Pemetaan status→tombol (ActionBar, hanya aksi dalam transisi):
- SCHEDULED: Mulai Produksi (start), Batalkan (cancel)
- IN_PROGRESS: Catat Hasil (yield)
- YIELD_COMPLETED: Cek QA (qa)
- QA_PASSED: Selesaikan (complete)
- QA_FAILED: Selesaikan (complete)
- COMPLETED, CANCELLED: terminal (tidak ada aksi)
Complete surface 400 (stok bahan kurang) di modal, user tetap di halaman.

Standar UI dipatuhi: header dokumen flex justify-between (Back icon-only ChevronLeft
rtl:rotate-180 + judul di START, ActionBar di END); section stateless terpisah; row

modal backdrop transparan + rounded-3xl; dark mode + RTL logical props + token warna;
