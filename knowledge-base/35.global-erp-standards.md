# 35. Global ERP Standards

This document establishes the global architectural standards, database schemas, and conventions for the Bakery ERP platform. All future modules must reuse these standards to maintain system-wide consistency.

---

## 1. Global Status Lifecycle

Every document or transaction entity must conform to a subset of the following standardized states:

| Status | Code | Description |
| --- | --- | --- |
| **Draft** | `DRAFT` | Document is work-in-progress and can be edited. |
| **Submitted** | `SUBMITTED` | Pending review/approval. Locked for edits. |
| **Approved** | `APPROVED` | Approved by supervisor. Operations can proceed. |
| **Rejected** | `REJECTED` | Rejected by supervisor. Can be reverted to Draft. |
| **Cancelled** | `CANCELLED` | Voided/archived. Permanent terminal state. |
| **Completed** | `COMPLETED` | Fully executed (e.g. goods received, production done). |
| **Closed** | `CLOSED` | Period locked for financial accounting/archiving. |

---

## 2. Numbering Convention

All transactional document numbers must utilize a year-prefix auto-incrementing serial format:

- **Format**: `[PREFIX]-[YYYY]-[SERIAL]`
  - `PREFIX`: 2-4 character uppercase identifier.
  - `YYYY`: 4-digit calendar year.
  - `SERIAL`: 6-digit zero-padded auto-incrementing sequence (resets every year).
- **Standards**:
  - Purchase Request: `PR-{outletNumberingCode}-YYYY-XXXXXX` (e.g. `PR-WH-RETAIL-01-2026-000001`)
  - Purchase Order: `PO-{outletNumberingCode}-YYYY-XXXXXX` (e.g. `PO-WH-RETAIL-01-2026-000001`)
  - Goods Receipt: `GR-YYYY-XXXXXX` (e.g. `GR-2026-000001`)
  - Purchase Return: `RTN-YYYY-XXXXXX` (e.g. `RTN-2026-000001`)
  - Vendor Invoice: `VINV-YYYY-XXXXXX` (e.g. `VINV-2026-000001`)
  - Stock Transfer: `TRF-YYYY-XXXXXX` (e.g. `TRF-2026-000001`)
  - Production Order: `PRD-YYYY-XXXXXX` (e.g. `PRD-2026-000001`)
  - POS Invoice: `INV-YYYYMMDD-XXXXXX` (Special date-based variant for high-frequency sales)

## 3. Global Permissions

Permissions are evaluated by code and rendered by metadata.

Every active permission must define:

- `domain`
- `moduleKey`
- `moduleName`
- `action`
- `displayName`
- `sortOrder`

Role Management must render permissions as:

```text
Business Domain
  -> Module
    -> Action
```

Legacy permissions without metadata must use an explicit deterministic compatibility mapping. They must never fall back to generic `Access` or `Audit` business groups.

### Canonical Domains
- Master Data
- Procurement
- Inventory
- Production
- Sales
- Finance
- System Administration
- Reports
- Settings

### Standard Action Order
- `read`
- `create`
- `update`
- `delete`
- `submit`
- `approve`
- `reject`
- `complete`
- `cancel`
- `reopen`
- `send`
- `comment`
- `attachment`
- `print`
- `export`
- `manage`

Do not rename existing permission codes only to change UI grouping.

Examples:

```text
payment-term.read       -> Master Data / Payment Term / Read
payment-term.manage     -> Master Data / Payment Term / Manage
procurement.pr.read     -> Procurement / Purchase Request / Read
procurement.po.approve  -> Procurement / Purchase Order / Approve
procurement.gr.complete -> Procurement / Goods Receipt / Complete
procurement.return.complete -> Procurement / Purchase Return / Complete
finance.vendor-invoice.verify -> Finance / Vendor Invoice / Verify
finance.vendor-invoice.post   -> Finance / Vendor Invoice / Post
```

Payment Term follows the existing Master Data permission convention used by UOM and Supplier:

`payment-term.read`
`payment-term.manage`

Payment Term is master data, not an enum. Documents that use it must persist snapshot fields required for historical readability. Purchase Orders may store an estimated payment due date, but Accounts Payable due dates are owned by Vendor Invoice / AP documents.

Vendor Invoice belongs to Finance. Its external Supplier invoice number must be normalized with `trim + uppercase`, unique per Supplier, and permanently reserved even when the ERP document is soft-deleted.

Vendor Invoice Three-Way Matching is a separate review result, not a document lifecycle status. A document may be `SUBMITTED` with a current matching status of `MATCHED` or `EXCEPTION`. Verification must perform a fresh authoritative match and may proceed only when the result is `MATCHED`.

Vendor Invoice posting is the finance boundary into Accounts Payable. `VERIFIED -> POSTED` must create the Accounts Payable obligation atomically in the same transaction, and must not occur when AP creation fails. Accounts Payable is a ledger obligation in the MVP; it uses its database ID plus Vendor Invoice references for traceability and does not introduce a separate AP document number. AP payment status is separate from `VendorInvoiceStatus`, and overdue is derived rather than persisted.

## 3.1 SaaS Tenant Foundation

The SaaS tenant boundary is `Company`. A user may belong to multiple companies through `CompanyMembership`. `Role` and `Permission` remain global templates during the compatibility phase, but tenant-aware endpoints must derive the effective role and permissions from `CompanyMembership.roleId`, not from legacy `User.roleId`.

JWT principal and tenant context are separate:

```text
JWT principal = who the user is
TenantContext = which Company the user is acting within
```

Active company context is request-scoped. Backend requests may carry `X-Company-Id`, but the backend must validate that the authenticated user has an ACTIVE membership in an active, non-deleted Company before creating `TenantContext`. If a user has exactly one active membership and no company header is provided, the backend may auto-resolve that company for compatibility. If multiple active memberships exist and no company header is provided, the request must fail with a deterministic active-company-required error.

Issue 1 of the SaaS refactor introduces Company/Membership foundation only. It does not claim full tenant isolation for legacy operational modules until business aggregates receive explicit company scope and legacy OWNER bypasses are migrated.

Issue 2 adds Outlet tenant ownership and membership outlet scope as foundation only:

```text
Outlet.companyId
CompanyMembershipOutlet
TenantContext.accessibleOutletIds
TenantContext.accessibleOutlets
```

`accessibleOutletIds` is always backend-derived. Non-OWNER memberships use explicit `CompanyMembershipOutlet` rows. A company-scoped OWNER automatically receives all non-deleted Outlets inside the active Company, but this never bypasses the Company boundary. Authorization scope is separate from operational eligibility: inactive Outlets may remain readable for historical data, while document creation/posting must apply separate active/capability rules.

SaaS Issue 3 certifies tenant-aware authorization for Procurement, Inventory read/mutation, and held Finance runtime paths.

SaaS Issue 4 makes tenant-specific Master Data company-scoped:

```text
ProductGroup.companyId
ProductCategory.companyId
Product.companyId
Supplier.companyId
PaymentTerm.companyId
Outlet.companyId
```

Codes/SKUs for these tenant-owned masters are unique inside a Company and may be reused by another Company. Runtime master-data endpoints must use `TenantContext.permissions` and derive `companyId` from the active tenant context; frontend forms must not submit `companyId` as user-controlled input. UOM remains a global canonical master for MVP. Document numbering remains global/legacy in Issue 4 and is deferred until business aggregate roots receive explicit `companyId`.

During Tenant Isolation Hardening, tenant-aware endpoints may use `TenantPermissionsGuard` as a transitional compatibility path. It must stay contract-compatible with the canonical permission guard and differ only in permission source: tenant-aware checks read `TenantContext.permissions`, which are resolved from the active `CompanyMembership.roleId`. The target architecture is one canonical permission contract, not two permanent authorization systems.

Frontend authorization must prefer active company context permissions over legacy `currentUser.permissions`. `currentUser.permissions` is a compatibility fallback only when tenant context has not been bootstrapped. Navigation/action visibility is UX support; backend TenantContext checks remain authoritative.

Finance held modules follow the same tenant boundary without enabling new workflow. Vendor Invoice and Accounts Payable access must be proven through `resource.outlet.companyId == TenantContext.companyId` and `resource.outletId in TenantContext.accessibleOutletIds`. Accounts Payable tenant provenance is derived through its Outlet and, when created from Vendor Invoice posting, must preserve the Vendor Invoice Outlet.

## 5. Reusable Attachment Standard

- **Supported File Types**: `application/pdf`, `image/jpeg`, `image/png`.
- **Max File Size**: 5 MB per file.
- **Storage Strategy**:
  - Local Disk (development): `/uploads/<module>/<year>/`
  - S3 / GCS (production): `s3://erp-bakery-bucket/<module>/<year>/`
- **Naming Convention**: `[DOC-NUMBER]-[TIMESTAMP].[EXT]` (e.g. `PR-2026-000001-1718012345.pdf`).

---

## 6. Reusable Comment Standard

Comments must be categorized using one of these four tags:

- `APPROVAL`: Written by supervisors during Approve/Reject actions.
- `INTERNAL`: Discussion note visible only to team staff.
- `EXTERNAL`: Notes printed on customer invoices or vendor PO dispatches.
- `SYSTEM`: Automatically logged by backend event triggers (e.g. "Status changed from Draft to Submitted").

## 8. Inventory Posting Source Keys

Inventory movements created from business documents must carry deterministic source metadata in addition to legacy `referenceType` and `referenceId`.

Required source fields:

- `sourceDocumentType`
- `sourceDocumentId`
- `sourceDocumentItemId`
- `sourceDocumentAllocationId`

For Goods Receipt inventory posting:

- `sourceDocumentType = GOODS_RECEIPT`
- `sourceDocumentId = GoodsReceipt.id`
- `sourceDocumentItemId = GoodsReceiptItem.id`
- `sourceDocumentAllocationId = GoodsReceiptBatch.id`
- `movementType = PURCHASE`

The database must prevent duplicate posting for the same source allocation and movement type. Reversal documents, including Purchase Return, must derive returnable stock from posted movement quantities instead of relying only on document item snapshots. Purchase Return inventory reversal uses the canonical inventory movement type `RETURN` and must be committed atomically with the document completion status.

Every `InventoryBatch.qtyAvailable` balance mutation must commit atomically with its `InventoryMovement` ledger entry and must use a concurrency-safe transaction strategy such as Serializable transaction retry. Direct read-compute-write stock updates without lost-update protection are forbidden.

Inventory reconciliation is read-only by default. It may compare `InventoryBatch.qtyAvailable` against ledger-derived balances and report integrity issues, but historical balance repair must never silently modify `InventoryBatch` or `InventoryMovement`; repair requires an explicit controlled correction workflow.

Stock On Hand is the canonical read view of current inventory and must read from `InventoryBatch.qtyAvailable`. `InventoryMovement` remains the immutable ledger and must not be used as the primary list-balance calculator for normal Stock On Hand requests.

Stock Ledger is the canonical read view of inventory history and must read from `InventoryMovement`. Posted movement rows are append-only ledger evidence; corrections must use explicit future counter/reversal transactions rather than editing or deleting historical movement records.

Batch & Expiry Management is a read-only InventoryBatch monitoring view. Expiry state must be derived on the backend from the canonical business date; the MVP expiring-soon threshold is 30 days and is a future configurable-policy candidate. Expired stock must remain visible and must not be auto-written-off or auto-adjusted without an explicit approved inventory transaction. Monitoring may present a derived operational status (an `ACTIVE` batch past its expiry displays as expired/unusable) without rewriting the stored lifecycle status; the stored `status` filter and the derived `operationalStatus` filter are separate contracts, and held or depleted batches are never reclassified by the calendar.

Stock Transfer is an inventory mutation document and must use the canonical stock mutation boundary. `SUBMITTED` locks the document without stock movement. Dispatch creates `TRANSFER_OUT` and decrements the exact source `InventoryBatch`; receive creates `TRANSFER_IN` and increments the deterministic destination `InventoryBatch`. Both steps must use concurrency-safe transactions and deterministic source keys. Completed transfer total quantity must not create stock gain/loss; any future loss/damage correction requires an explicit reversal or adjustment workflow.

Stock Adjustment is an explicit inventory correction document, not a direct stock edit. Draft create/update stores adjustment intent only. Completion must reload the exact `InventoryBatch`, derive authoritative before/after quantities, update `InventoryBatch.qtyAvailable`, create `ADJUSTMENT_IN` or `ADJUSTMENT_OUT` ledger rows, and write history in one concurrency-safe transaction. New executable adjustment posting must not use legacy `ADJUSTMENT`, which remains a historical/diagnostic movement type.

Stock Opname is a physical stock counting document. Starting a count captures frozen `InventoryBatch.qtyAvailable` snapshots and locks the outlet against inventory mutations while status is `COUNTING`, `SUBMITTED`, or `APPROVED`. Completion must not directly mutate stock; non-zero variance must flow through exactly one generated Stock Adjustment linked to the Stock Opname and posted by the canonical adjustment engine. Zero variance completes without creating adjustment movements.

Inventory hardening and database-backed concurrency tests must use an isolated test database configured by `INVENTORY_INTEGRATION_DATABASE_URL`. The URL must be present, must not equal `DATABASE_URL`, and must identify a test-only database before any fixture setup runs. Test cleanup must target only records created by the test fixture; hardening tests must never reset or mutate the normal development database.
