# ROLE & PERMISSION SYSTEM

The system enforces Permission-Based Authorization.

- **Role Codes**: Immutable technical identifiers (`OWNER`, `SUPERVISOR_OUTLET`, `ADMIN_GUDANG`, `PRODUKSI`, `KASIR`).
- **Display Names**: Friendly business titles (Business Owner, Outlet Supervisor, Outlet Staff, Production Staff, Cashier).
- **Authorization Flow**: Guards, endpoints, and frontend visibility must only check Permission strings (e.g. `product.read`, `sales.manage`), never Role Codes.
- **Sprint 1 Policy**: Permissions are mapped to roles in `prisma/seed.ts` and are read-only via the UI.
- **Business Roles Only**: Every Role must represent an actual business position or operational function (e.g. OWNER, SUPERVISOR_OUTLET, ADMIN_GUDANG, PRODUKSI, KASIR). Future roles: `PURCHASING_OFFICER`, `FINANCE_ADMIN`, `OPERATIONS_MANAGER`.
- **No Fallback/Other Roles**: Generic roles like `Other`, `Miscellaneous`, `General`, `Unknown`, or `Undefined` must never be introduced automatically. If classification fails, request clarification or recommend a new business role instead.
- **Role Creation**: New roles must satisfy: real business function, clear responsibility, defined permission set, documented in the Role & Permission Matrix, and approved.
- **Permission Classification Policy**:
  - The "Other" permission category/group is strictly prohibited and must never be generated or used.
  - Every permission must belong to exactly one of the 10 permission-enabled Business Modules:
    - `user.*`, `role.*`, `permission.*`, `audit.*` → **System Administration**
    - `outlet.*`, `supplier.*`, `product-group.*`, `category.*`, `uom.*`, `product.*` → **Master Data**
    - `procurement.pr.*`, `procurement.po.*`, `procurement.gr.*` → **Procurement**
    - `inventory.*`, `stock-adjustment.*`, `stock-opname.*`, `stock-transfer.*`, `replenishment.*` → **Inventory**
    - `recipe.*`, `bom.*`, `production.*` → **Production**
    - `distribution.*`, `delivery-order.*`, `inter-outlet-transfer.*` → **Distribution**
    - `sales.*`, `shift.*`, `pos.*` → **Sales & POS**
    - `payment.*`, `expense.*`, `cashflow.*` → **Finance**
    - `dashboard.*`, `report.*` → **Reporting**
    - `setting.*`, `company.*` → **Settings**
  - If a new permission does not match any prefix above, determine the most appropriate business domain based on its prefix. If no domain fits, flag it for manual review.
- **Source of Truth**: The Role & Permission Matrix, ADRs, Knowledge Base, and approved implementation plans are the absolute source of truth.

# BUSINESS RULES

## Inventory

* Negative stock is prohibited.
* Every stock change must create inventory movement.
* Every stock transaction must create audit log.

---

## Batch Rules

Batch tracking is mandatory for:

* Raw Materials
* Finished Goods
* Semi Finished Goods

Each batch contains:

* Batch Number
* Expired Date
* Available Quantity

---

## FEFO RULES

Inventory consumption uses:

FEFO (First Expired First Out)

Algorithm:

1. Select ACTIVE batches.
2. Exclude expired batches.
3. Sort by expiry ascending.
4. Consume nearest expiry batch first.

Pseudo SQL:

```sql
SELECT *
FROM inventory_batches
WHERE qty_available > 0
AND expired_date > NOW()
ORDER BY expired_date ASC;
```

FEFO must be implemented in Service Layer.

---

## Production Rules

Production approval is not required.

Production flow:

1. Create Production Order.
2. Calculate material requirement.
3. Allocate FEFO batches.
4. Consume materials.
5. Create finished goods batch.
6. Record inventory movement.

---

## Replenishment Rules

* Request stock to Central Outlet.

Workflow:

Outlet
→ Create Request
→ Owner Approval
→ Create Transfer
→ Receive Transfer

---

## Sales Rules

Sales must:

* Automatically use FEFO.
* Generate invoice.
* Create payment.
* Reduce inventory.
* Create inventory movement.

Expired products cannot be sold.
