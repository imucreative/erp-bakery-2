# 21. Definition of Done (DoD)

This document defines the mandatory project-wide completion criteria that every feature and module must satisfy before it can be considered complete, reviewed, and ready for deployment.

---

## 1. Functional Alignment
- **Business Correctness**: The business requirement described in the PRD/BRD must be fully met.
- **Acceptance Criteria**: All acceptance criteria defined in user stories must be verified and pass.

---

## 2. Architectural Integrity

Every implementation must align with the Project Constitution layers:
- **Constitutions Compliance**: Must conform strictly to [19.frontend-constitution.md](file:///d:/antigravity/erp-bakery-2/knowledge-base/19.frontend-constitution.md) and [20.backend-constitution.md](file:///d:/antigravity/erp-bakery-2/knowledge-base/20.backend-constitution.md).
- **ERP UI Foundation**: Features must only compose layouts, tables, forms, and inputs using baseline components from `components/erp/*`.
- **Precedence Chain Compliance**:
  - Feature follows [24.ai-operating-system.md](file:///d:/antigravity/erp-bakery-2/knowledge-base/24.ai-operating-system.md) (AI Operating System).
  - Feature follows Knowledge Base specifications.
  - Feature follows the respective Frontend/Backend Constitution.
- **Zero Duplications**:
  - No duplicated implementation patterns or business functions.
  - No duplicated UI elements or local component overrides.

---

## 3. UI/UX Consistency

- **Mobile Responsiveness**: Viewports, tables (using horizontal scroll overlays), and form dialogs must scale and work correctly on small screen boundaries.
- **Dark Mode**: All colors, borders, and text contrasts must fully support light and dark themes.
- **State Feedback**:
  - **Loading**: Render explicit loaders (e.g., `ERPTableSkeleton`, `ERPLoading`).
  - **Empty**: Show `ERPEmpty` placeholders when data query returns 0 rows.
  - **Error**: Gracefully catch network failure and display descriptive banners.
  - **Notification**: Show success/error toasts (`ERPNotification`) upon action completion.
  - **Mutation Feedback**: Every user-triggered mutation must provide explicit success or failure feedback. Useful backend validation messages must be surfaced, and failed mutations must keep the user on the current page with their current form/document state preserved.

---

## 4. Code Quality & Cleanliness

- **No Duplicated Code**: Standard functions and utility mappings must be reused.
- **No Unused Code**: Clean up unused imports, dead variables (`noUnusedLocals`), and unused function parameters.
- **Clean Naming Conventions**: Files, functions, components, and variables must follow project coding standards (camelCase for methods, PascalCase for components, UPPERCASE for constants).

---

## 5. Security & Authorization

- **Permission Checking**: Every controller route and frontend layout page must enforce permissions check (never Role Codes) matching the matrix.
- **Payload Validation**: NestJS API routes must use class-validators and DTO schemas to validate payload properties, types, and constraints.

---

## 6. Performance Optimization

- **React Query Cache**: Re-use fetched data caching, set stale times, and invalidate key queries upon writes.
- **Paginated Fetching**: Implement limit/page parameters on list queries to prevent high memory footprints.
- **Memoization**: Memoize expensive rendering or layout calculations (`useMemo`, `useCallback`) where appropriate to prevent lag.

---

## 7. Verification Standards

- **Successful Compilation**: Both frontend and backend projects must compile cleanly (`npx tsc --noEmit` checks must pass with zero errors).
- **ESLint & Warning Audits**: Ensure no syntax or style warnings remain in compile logs.

---

## 8. Governance & Modifications

These rules represent a permanent element of the Project Constitution. Future modifications to the definition of done criteria require:
- An approved **Architecture Decision Record (ADR)**, or
- Explicit user approval.
