# 20. Backend Constitution

This document is the **canonical backend architecture constitution** for the Bakery ERP project. All future backend implementation rules, features, APIs, and refactorings must reference and adhere to this document instead of duplicating or redefining architectural rules elsewhere.

---

## 1. Layered Architecture

The backend monolith is structured into four strict, decoupled layers:

```
Controller (Routing, DTO mapping, HTTP responses)
   │
   ▼
Service (Business logic coordination, validations, transactions)
   │
   ▼
Repository (Data access layer abstraction)
   │
   ▼
Prisma (ORM & Database Client queries)
```

1. **Controller Layer**: Coordinates incoming REST requests, enforces JWT and permission middlewares, maps request bodies to DTOs, and handles HTTP response outputs. No business logic or database queries.
2. **Service Layer**: Houses the core domain rules, coordinates validations, handles access checks, and manages database transaction boundaries.
3. **Repository Layer**: Encapsulates DB operations and hides ORM (Prisma) complexities. Provides clean, contract-aligned querying helper functions.
4. **Prisma Layer**: Direct mapping of database schemas, indexes, and tables.

---

## 2. Dependency Rules

### Allowed Imports:
- Controllers may import DTOs, interfaces, and Services.
- Services may import DTOs, repositories, and helper utilities.
- Repositories may import database interfaces and Prisma client types.

### Forbidden Imports:
- Controllers **must never** import Prisma or query the database directly.
- Repositories **must never** import Services or Controllers (no circular dependencies).
- Entities or files outside the DB layer must not access Prisma Client directly.

---

## 3. Service & Business Logic Rules

- **Logic Location**: Core business logic, pricing computations, stock deductions, and validation rules must reside strictly inside Services.
- **Validation Responsibilities**: Services must perform logic checks (e.g. verify if a batch is active, verify stock availability) before executing mutations. Request payload data checks must be done using NestJS class-validators.
- **Transaction Boundaries**: DB queries requiring multi-table consistency (e.g., creating a Stock Opname and writing inventory movements) must be wrapped inside Prisma Transactions (`prisma.$transaction`) managed within the service scope.

---

## 4. Repository Rules

- **Database-Only Responsibilities**: Repositories are strictly responsible for database querying, sorting, pagination, and fetching operations.
- **No Business Logic**: Repositories must not evaluate business rules, permissions, or calculations. They only receive parameters, query the database, and return results.

---

## 5. API Design Conventions

### A. REST Guidelines
- All endpoints must follow lowercase plural REST conventions (e.g., `/api/v1/outlets`, `/api/v1/suppliers`).
- Standard action mappings:
  - `GET /` -> List items (paginated)
  - `GET /:id` -> Detail view
  - `POST /` -> Create item
  - `PUT /:id` -> Update item
  - `DELETE /:id` -> Soft-delete / deactivate item

### B. Response & Error Format
- Success payloads must return:
  ```json
  {
    "success": true,
    "data": { ... },
    "meta": { "page": 1, "limit": 10, "total": 120 } // if list view
  }
  ```
- Error payloads must use standard HTTP status codes and return:
  ```json
  {
    "success": false,
    "message": "Descriptive error message",
    "errors": []
  }
  ```

### C. Query Parameters (List Views)
- **Pagination**: Mandatory `page` and `limit` query parameters.
- **Filtering**: Query parameters for `search` and column filters (e.g., `status=ACTIVE`).
- **Sorting**: Mandatory `sortBy` (field name) and `sortOrder` (`asc` | `desc`) parameters.

---

## 6. Security Rules

- **Authentication**: All protected routes require a valid JWT bearer token verified via authentication guards.
- **Authorization**: Access must be authorized using granular permission guards (e.g. `@RequirePermission('product.create')`), never by raw user Role Codes.
- **Audit Logging**: Any write mutations (Create, Update, Delete) must create a non-repudiable audit log entry containing the user ID, timestamp, and changes diff.

---

## 7. Performance & Optimization

- **Query Efficiency**: Always select specific columns instead of querying full tables where possible. Eagerly load relationships (`include`) only when necessary.
- **Transaction Isolation**: Limit transactions to only include write queries. Do not wrap slow external API calls or email notifications inside DB transactions.
- **Indexes**: Prisma schema must define database indexes on frequently searched, filtered, or joined columns (e.g. foreign keys, code prefixes, status tags).

---

## 8. Governance & Modifications

These rules represent a permanent element of the Project Constitution. Future modifications, changes in database patterns, or updates to API protocols require:
- An approved **Architecture Decision Record (ADR)**, or
- Explicit user approval.
