# 43. Document Authorization Standard

This document establishes the standardized Document Authorization model to be used across all document-based modules in the Bakery ERP (e.g. Purchase Requests, Purchase Orders, Goods Receipts, Production Orders, Sales Orders, etc.).

---

## 1. Core Architecture

All document modules must delegate authorization evaluation to the global, injectable `DocumentAuthorizationService`.

Authorization must never be evaluated directly inside controller methods or scattered across ad-hoc helpers.

### Evaluation Parameters
Every access check is evaluated using:
1. **Permission**: Does the user hold the necessary granular domain permission (e.g. `procurement.pr.read`)?
2. **Outlet Scope**: Does the user's outlet match the document's outlet?
3. **Document Ownership**: Is the action restricted to the creator/requestor of the document?
4. **Document Status**: Is the document in an acceptable status state for the requested action?

Permission metadata (`domain`, `moduleKey`, `moduleName`, `action`, `displayName`, `sortOrder`) is used for Role Management grouping and display only. Document guards and services continue to authorize against stable permission codes.

### SaaS Compatibility Note

During the SaaS core refactor, `Company` becomes the tenant boundary and `CompanyMembership` owns tenant-aware role semantics. Existing document modules still use the legacy outlet-scope authorization model until their aggregate roots are migrated to explicit `companyId`. Any new tenant-aware endpoint must validate `TenantContext` from active company membership before evaluating outlet/document rules. Legacy `OWNER` outlet bypass must not be interpreted as global cross-company access.

SaaS Issue 2 introduces backend-derived outlet authorization scope on `TenantContext`:

```text
accessibleOutletIds subset of Outlets owned by active Company
```

Non-OWNER memberships receive outlet scope from explicit `CompanyMembershipOutlet` assignments. OWNER receives all non-deleted Outlets in the active Company only. Existing document modules are not yet migrated to this foundation; that migration belongs to Tenant Isolation Hardening.

Tenant-aware document authorization must prove outlet scope with `resourceOutletId in TenantContext.accessibleOutletIds`. It must not use `role === OWNER` as a global shortcut. OWNER all-outlet behavior is represented by the backend-derived accessible outlet set for the active Company.

Tenant Isolation Hardening migrates modules batch by batch. Migrated Procurement, Inventory, Vendor Invoice, and Accounts Payable paths must use `TenantContext` and membership-derived permissions; legacy `User.outletId`, JWT/global permissions, and global OWNER bypasses are compatibility-only outside migrated runtime paths.

Company-scoped Master Data must follow the same tenant principle. Product Group, Product Category, Product, Supplier, Payment Term, and Outlet master endpoints must derive `companyId` from `TenantContext`, apply company scope before pagination/search, block direct-ID access across companies, and validate same-company master references. UOM remains global canonical and is not company-scoped in the MVP.

Finance held compatibility is authorization hardening only. Vendor Invoice posting remains the finance boundary into Accounts Payable and must revalidate the authoritative Vendor Invoice tenant scope inside the posting transaction before creating AP. The refactor must not enable payment, settlement, journal, credit/debit note, or new Finance workflows.

## 2. Visibilty & Scoping

### Read Permission
A user can view/read a document only if:
- They hold the `read`, `approve`, or `manage` permission for the document.
- The document is not soft deleted.
- **Outlet Scope Rule**: The user belongs to the same outlet as the document.
  - **Owner Exception**: Users with the `OWNER` role bypass the outlet scope matching and can view documents across all outlets. Other roles must match the outlet exactly.

### Listing Filtering
List query endpoints must apply the same outlet scoping rules directly to the database query filters:
- Non-Owner users are filtered using `where.outletId = user.outletId`.
- Owners retrieve all records.

---

## 3. Creation & Modifications

### Creation
- Requester must hold `create` or `manage` permissions.
- The document automatically inherits the creator's assigned `outletId` at creation.
- The `outletId` is immutable and cannot be changed manually during updates.

### Update, Delete, & Cancellation
Only the creator of the document is allowed to edit, delete, or cancel it. Roles configured as outlet-bypass roles, such as `OWNER`, can also bypass ownership when they hold the required permission.
- **Permissions**: Requester must hold `update` or `manage` permissions.
- **Outlet Scope**: Matches the creator's outlet (Owner bypass applies).
- **Status Validation**: The document must be in an editable status state:
  - Editable statuses: `DRAFT`, `REJECTED`.
  - Non-editable statuses: `SUBMITTED`, `APPROVED`, `CANCELLED`.

---

## 4. Workflows & Collaborations

### Approval
- Requester must hold `approve` or `manage` permissions.
- Document must be in `SUBMITTED` status.
- **Sequence Matching**: The requester's role must match the active pending approval step's `approverRole` (Owner bypass applies).
- **Rejection Comment**: A rejection action strictly requires a mandatory comment, whereas comments on approval remain optional.

### Comments
- Commenting requires `canRead()` access first.
- The user must hold `create`, `approve`, or `manage` permissions.

### Attachments
- **Upload**: Uploading new attachments follows the same rules as Comments.
- **Immutability**: Once a document is submitted (non-DRAFT/non-REJECTED status), existing attachments become immutable and cannot be modified or deleted. Only new attachments can be added.

---

## 5. Audit Logging

Every status transition or document update must write an audit record to the module's history log containing:
- `actorId` (Actor User UUID)
- `actorRole` (Actor Role Code)
- `actorOutletId` (Actor Outlet UUID)
- `previousStatus`
- `newStatus`
- `comment`
- `metadata` (JSON field)

### Reserved Metadata Keys
To support future security audits, the `metadata` JSON field must always reserve the following placeholders:
- `ipAddress: null`
- `userAgent: null`
- `requestId: null`

---

## 6. Future Guards & Decorators Extension

Future implementations will support a declarative NestJS guard pattern:

```typescript
@UseGuards(DocumentAccessGuard)
@RequireDocumentAccess({
  policy: PurchaseRequestPolicy,
  action: 'read'
})
@Get(':id')
async findOne(@Param('id') id: string) { ... }
```

The guard will inject `DocumentAuthorizationService` to inspect user context and doc context before entering the handler.
