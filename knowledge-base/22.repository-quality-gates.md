# 22. Repository Quality Gates

This document defines the mandatory repository quality gates that every feature development or refactoring task must pass before it can be marked as complete, approved for merge, or declared Done.

---

## 1. The Quality Gates

### A. Architecture Gate
- Verify that the implemented feature strictly follows [19.frontend-constitution.md](file:///d:/antigravity/erp-bakery-2/knowledge-base/19.frontend-constitution.md) and [20.backend-constitution.md](file:///d:/antigravity/erp-bakery-2/knowledge-base/20.backend-constitution.md).
- Validate that all layers (Controller, Service, Repository, Database) are separated cleanly.

### B. UI Foundation Gate
- Ensure that no feature component imports from `@/components/ui/*` or uses raw HTML input tags.
- Confirm all button structures utilize `ERPButton` and actions compose `ERPTableActions`.

### C. Code Quality Gate
- Run an analysis to verify no duplicated logic or copied markup exists.
- Clean up unused imports, dead variables, and resolve ESLint warnings.
- Confirm names of files, variables, and properties conform to standard naming conventions.

### D. Security Gate
- Enforce that all routes and pages verify permission parameters against the role-permission matrix.
- Ensure all API body schemas validate inputs using class-validators.

### E. Performance Gate
- Inspect database queries to verify only specific columns are loaded and indexes are used.
- Check that client components optimize state updates to avoid redundant re-renders.

### F. Build Gate
- **Backend check**: Ensure `npx tsc --noEmit` compiles successfully with zero warnings/errors.
- **Frontend check**: Ensure `npx tsc --noEmit` (or dev build compilation) succeeds.

### G. Review Gate
- Confirm the implementation fully respects [24.ai-operating-system.md](file:///d:/antigravity/erp-bakery-2/knowledge-base/24.ai-operating-system.md).
- Verify the feature does not duplicate existing patterns in other modules.

### H. Knowledge Base Update Rule
- If the implementation introduces:
  - Any new architecture pattern,
  - A new reusable component,
  - A new design token/pattern, or
  - A new workflow sequence,
- The related **Knowledge Base document must be updated** and synchronized to reflect the changes before the task can be marked as complete.

### I. Release Gate
- All the above gates (A through H) must pass successfully before marking work as Done.

---

## 2. Governance & Modifications

These rules represent a permanent element of the Project Constitution. Future modifications to the repository quality gates require:
- An approved **Architecture Decision Record (ADR)**, or
- Explicit user approval.
Other Knowledge Base documents should reference these rules instead of redefining architectural gates.
