## 1. Tujuan

Super Admin dapat mengelola role **per company** dari Platform Console: melihat daftar,
melihat detail permission, membuat, mengubah (nama/deskripsi + full-sync permission), dan
menghapus role — tanpa harus login sebagai user tenant.

Prinsip yang dipertahankan:

1. Role tetap **company-scoped** (`roles.company_id`). Plan ini **tidak** membuat katalog
   role global (`company_id NULL`).
2. Seluruh endpoint baru wajib `@SuperAdminOnly()`; guard yang ada mensyaratkan Super Admin
   **dan 2FA aktif**.
3. Permission domain `system-administration` (8 kode, doc 16) **tidak boleh** diberikan ke
   role company mana pun.
4. Semua mutasi menulis `audit_logs` dengan module `platform_roles`.
5. Guardrail role yang sudah ada dipertahankan: `code` immutable & unik per company, OWNER
   tidak bisa dihapus, role yang masih dipakai user aktif tidak bisa dihapus.

**Tidak perlu migrasi baru** — tabel `roles`, `role_permissions`, `permissions`, dan
`audit_logs` sudah tersedia (migrasi tersedia sampai 074).

## 4. Kontrak API

Semua path di bawah `@SuperAdminOnly()` + guard 2FA yang sudah ada. Response memakai
envelope `successResponse` / `listResponse`.

| Method | Path | Fungsi | Status sukses |
|--------|------|--------|---------------|
| GET | `/api/v1/platform/companies/:companyId/roles` | Daftar role company + `description`, `userCount` | 200 |
| GET | `/api/v1/platform/companies/:companyId/roles/:roleId` | Detail role + permission codes | 200 |
| POST | `/api/v1/platform/companies/:companyId/roles` | Buat role + permission awal | 201 |
| PUT | `/api/v1/platform/companies/:companyId/roles/:roleId` | Ubah nama/deskripsi dan/atau full-sync permission | 200 |
| DELETE | `/api/v1/platform/companies/:companyId/roles/:roleId` | Hapus role | 200 |
| GET | `/api/v1/platform/permissions` | Katalog permission global (untuk picker) | 200 |

DTO create/update **memakai ulang** `CreateRoleDto` dan `UpdateRoleDto` milik modul roles
(`Interfaces/http/api/roles/dto/`) agar kontrak tenant dan platform identik. `code` tetap
tidak ada di DTO update.

### Validasi & error

| Kondisi | Error code | HTTP |
|---------|-----------|------|
| `companyId`/`roleId` bukan UUID valid | `COMPANY.NOT_FOUND` / `ROLE.NOT_FOUND` (validasi format sebelum query) | 404 |
| Company tidak ada / sudah dihapus | `COMPANY.NOT_FOUND` | 404 |
| Role tidak ada **atau** milik company lain **atau** role platform (`company_id NULL`) | `ROLE.NOT_FOUND` | 404 |
| `code` duplikat dalam company | `ROLE.CODE_ALREADY_USED` | 409 |
| Permission code tidak ada di katalog | `ROLE.PERMISSION_UNKNOWN` | 400 |
| Permission code sistem dikirim | `ROLE.PERMISSION_RESERVED` (**baru**) | 400 |
| Hapus OWNER | `ROLE.OWNER_CANNOT_BE_DELETED` | 409 |
| Hapus role yang masih dipakai user aktif | `ROLE.IN_USE` | 409 |

Company suspended **tetap boleh** dikelola role-nya (tidak ada gate `is_active`); tujuannya
agar operator dapat memperbaiki akses sebelum mengaktifkan kembali company.

### Audit

`audit_logs.module` harus dapat diisi per operasi. `PlatformRepository.recordAudit()` saat
ini menghardcode `'platform_users'`; ubah signature menjadi menerima `module` (perbarui tiga
call site user) lalu tulis:

- CREATE → `oldValue: null`, `newValue: { code, name, permissions }`
- UPDATE → `oldValue: { name, description, permissions }`, `newValue: { ... }` (snapshot
  sebelum/sesudah; permission dibaca via repository)
- DELETE → `oldValue: { code, name, description, permissions }`, `newValue: null`

`entity_id` = `role.id`, `company_id` = company pemilik role.

## 5. Backend — perubahan per increment

### B1. Guardrail permission sistem

- Tambah `backend/src/Domains/roles/rolePolicy.ts`:
  - `RESERVED_PERMISSION_CODES` = 8 kode doc 16 (`user.read`, `user.manage`, `role.read`,
    `role.manage`, `permission.read`, `permission.manage`, `audit.read`, `auth.manage`).
  - `findReservedPermissions(codes: string[]): string[]`.
- `CreateRoleUseCase` & `UpdateRoleUseCase`: setelah `_verifyPermissionsExist`, tolak bila
  ada kode reserved → `throw new Error('ROLE.PERMISSION_RESERVED')`.
- Hapus `OWNER_ROLE_CODE`/`ROLE_MANAGE_PERMISSION` dan `_enforceOwnerGuardrail` dari kedua
  use case (keputusan D4).
- `Commons/exceptions/DomainErrorTranslator.ts`: daftarkan `ROLE.PERMISSION_RESERVED` sebagai
  `InvariantError` dengan pesan Indonesia yang menyebut permission tersebut hanya untuk
  Super Admin.

### B2. Atomisitas pembuatan/perubahan role

Saat ini `addRole()` lalu `setRolePermissions()` berjalan pada transaksi terpisah; bila
langkah kedua gagal, role tanpa permission tertinggal. Demikian pula `updateRole()` +
`setRolePermissions()`.

- Tambah method abstrak di `Domains/roles/RoleRepository.ts`:
  - `addRoleWithPermissions(data, permissionCodes): Promise<string>`
  - `updateRoleWithPermissions(id, companyId, data, permissionCodes): Promise<Role>`
- Implementasi `RoleRepositoryPostgres` memakai satu `client` dengan `BEGIN/COMMIT/ROLLBACK`;
  pemetaan unique violation (`23505`) tetap menghasilkan `ROLE.CODE_ALREADY_USED`.
- `CreateRoleUseCase`/`UpdateRoleUseCase` memakai method baru tersebut; method lama tetap
  dipakai bagian lain bila masih diperlukan.
- Unit test: kegagalan insert permission membatalkan insert/update role (rollback), dan
  permission lama tidak hilang saat update gagal.

### B3. Endpoint platform

`Interfaces/http/api/platform/platform.controller.ts` — tambah dependency:
`CompanyRepository`, `RoleRepository`, `PermissionRepository`, `CreateRoleUseCase`,
`UpdateRoleUseCase`, `DeleteRoleUseCase`.

- Helper `_assertCompanyExists(companyId)` → `companyRepository.getCompanyById(companyId)`
  (melempar `COMPANY.NOT_FOUND`).
- List: ganti pemakaian `platformRepository.listRoles()` dengan query yang mengembalikan
  `description` + `userCount` (extend `PlatformRepository.listRoles`/`PlatformRoleItem`;
  `LEFT JOIN users` dengan `deleted_at IS NULL`, group by role).
- Detail: `roleRepository.getRoleByIdAndCompany(roleId, companyId)` (otomatis menolak role
  company lain/platform) + `getRolePermissions`.
- Create/Update/Delete: delegasikan ke use case tenant dengan `companyId` dari path, lalu
  tulis audit (lihat §4). Untuk update, baca snapshot lama sebelum eksekusi.
- `GET platform/permissions`: panggil `permissionRepository.getAllPermissions()`; jangan
  bergantung pada bypass permission Super Admin.
- Swagger: tambahkan `@ApiOperation`/`@ApiResponse` 400/403/404/409.

Tidak ada perubahan `InfrastructureModule` selain bila provider `CompanyRepository` belum
tersedia sebagai token (verifikasi saat implementasi; `PlatformController` dirakit di
`InfrastructureModule`).

### B4. Registrasi & tes backend

- `CreateRoleUseCase.test.ts` / `UpdateRoleUseCase.test.ts`: tambah kasus reserved dan hapus
  ekspektasi OWNER `role.manage`; pertahankan kasus validasi/unknown permission.
- Test `RoleRepositoryPostgres.test.ts` (bila memungkinkan dengan pola yang ada): rollback
  transaksi baru.

## 7. Keamanan & konsistensi

- Company context **selalu** dari path + validasi role-company; tidak pernah dari body/JWT
  Super Admin (yang tidak punya company).
- Role platform (`company_id NULL`) dan user SUPER_ADMIN tidak pernah muncul/tersentuh.
- Reserved permission ditolak dua lapis (picker + backend).
- Audit wajib untuk create/update/delete; kegagalan audit tidak boleh membuat role berubah
  tanpa jejak — tulis audit setelah use case sukses dan biarkan request gagal bila audit
  gagal (perilaku sama dengan mutasi user platform saat ini; catat sebagai batas).
- Last-write-wins pada full-sync permission; dua operator yang mengedit bersamaan dapat
  saling menimpa. Dicatat sebagai batas, bukan bug pada increment ini.

## 8. Verifikasi

### Unit test
- Reserved permission ditolak (create & update).
- OWNER tidak lagi dipaksa `role.manage`; OWNER tetap tidak dapat dihapus.
- Rollback transaksi role+permission.
- Scoping company: role company lain → `ROLE.NOT_FOUND`.

### Gates
- Backend: `npx nest build` (dari `backend/`), `npx jest -i roles`.
- Frontend: `npm run type-check`, `npx eslint` hanya file yang berubah, `npx prettier --check`.

### E2E manual (server agent di port 5001, Vite 5175; port 5000/5174 milik user)
1. Login Super Admin dengan 2FA aktif → buka `/platform/roles`.
2. Pilih company → list role; buat role baru dengan beberapa permission → muncul di list.
3. Buka detail → permission sesuai; edit nama + ubah permission → tersimpan.
4. Kirim permission reserved (via API) → 400 `ROLE.PERMISSION_RESERVED`.
5. Hapus role baru → hilang; hapus role yang dipakai user aktif → 409 `ROLE.IN_USE`;
   hapus OWNER → 409 `ROLE.OWNER_CANNOT_BE_DELETED`.
6. Assign role baru ke user tenant lewat Platform Users → login user tersebut → menu sesuai
   permission (perlu refresh token ≤15 menit).
7. Non-Super Admin memanggil endpoint platform → 403; Super Admin tanpa 2FA → ditolak guard.
8. Regresi tenant: halaman `/system/roles` tetap berfungsi untuk user yang punya `role.read`.
9. Periksa baris `audit_logs` module `platform_roles` untuk create/update/delete.

Setelah verifikasi: hentikan hanya server yang dijalankan agent.
