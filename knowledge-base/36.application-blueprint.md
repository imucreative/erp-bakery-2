This document defines the standardized directory layouts, naming conventions, absolute import rules, and dependency structures for both the NestJS backend and Next.js frontend of the Bakery ERP.

---

## 1. Backend Folder Structure Standard (NestJS)

Every feature module in the backend monolith must be located under `backend/src/modules/<feature-name>/` and follow this strict structural layout:

```text
src/modules/<feature-name>/
├── controllers/          # HTTP request handlers and routing
│   └── <feature-name>.controller.ts
├── services/             # Core business logic execution and transactions
│   └── <feature-name>.service.ts
├── repositories/         # Database access abstraction (ORM-free interface calls)
│   └── <feature-name>.repository.ts
├── dto/                  # Data Transfer Objects for validation
│   ├── create-<feature-name>.dto.ts
│   └── update-<feature-name>.dto.ts
├── entities/             # Domain entity definitions
│   └── <feature-name>.entity.ts
├── interfaces/           # TS Interfaces or type mappings
│   └── <feature-name>.interface.ts
├── tests/                # Unit and integration tests
│   ├── <feature-name>.service.spec.ts
│   └── <feature-name>.controller.spec.ts
└── <feature-name>.module.ts # NestJS Module definition
```

## 2. Frontend Folder Structure Standard (Next.js)

Extending the rules defined in [31.erp-module-blueprint.md](file:///d:/antigravity/erp-bakery-2/knowledge-base/31.erp-module-blueprint.md), the Next.js App Router workspace is organized as follows:

```text
src/app/(dashboard)/<feature-name>/
├── page.tsx               # Client component orchestrator
├── components/            # Stateless view-only dashboard layout parts
│   ├── <feature-name>-columns.tsx
│   ├── <feature-name>-table.tsx
│   ├── <feature-name>-filter-bar.tsx
│   ├── <feature-name>-form-dialog.tsx
│   ├── <feature-name>-delete-dialog.tsx
│   └── index.ts
├── hooks/                 # Custom React hooks (queries and mutations)
│   ├── use-get-<feature-name>s.ts
│   └── use-create-<feature-name>.ts
├── services/              # API wrapper services
│   └── <feature-name>.service.ts
├── schemas/               # Zod validation schemas
│   └── <feature-name>.schema.ts
├── types/                 # TypeScript type interfaces
│   └── <feature-name>.type.ts
└── constants/             # Static configurations and route definitions
```

## 3. Naming Conventions

To keep file navigation intuitive and automated scripts running cleanly, these naming rules are enforced:

| Target | Convention | Example |
| --- | --- | --- |
| **Folders & Files** | `kebab-case` | `purchase-request-columns.tsx`, `purchase-request/` |
| **Classes & Components** | `PascalCase` | `PurchaseRequestService`, `ERPDataTable` |
| **Variables & Functions** | `camelCase` | `totalEstimatedAmount`, `calculateSubtotal()` |
| **Interfaces & Types** | `PascalCase` | `PurchaseRequest`, `IPurchaseRequestRepository` |
| **Enums & Constants** | `UPPER_SNAKE_CASE` | `STATUS_DRAFT`, `DEFAULT_PAGE_LIMIT` |
| **Database Tables (Prisma)**| `camelCase` | `purchaseRequest`, `purchaseRequestLineItem` |

## 4. Import Rules

- **Absolute Aliases**: All imports must utilize absolute root prefixes configured in `tsconfig.json`.
  - Backend: `import { ... } from '@/modules/auth/...'`
  - Frontend: `import { ... } from '@/components/erp/...'`
- **No Relative Parent Traversals**: Parent relative imports (e.g. `import { ... } from '../../../../components'`) are strictly forbidden. Use aliases.
- **Clean Barrel Exports**: Folders containing components (`components/`) must expose an `index.ts` barrel file to clean up import statements in `page.tsx`.
