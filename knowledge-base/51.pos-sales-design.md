## 1. Business Purpose & Scope

### 1.1 Tujuan
Modul POS / Sales menangani transaksi penjualan di titik jual (outlet): membuka/menutup
shift kasir, membangun keranjang (cart) produk + topping, melakukan checkout dan pembayaran,
lalu **mengurangi stok secara otomatis via FEFO saat pembayaran berhasil**, serta menangani
retur/refund. POS mendukung **dua mode penjualan per produk** (keputusan OQ-3):
- **MADE_TO_ORDER** — produk punya resep ACTIVE; saat PAID sistem **backflush bahan** (adonan +
  topping) via FEFO (movement `SALE`), seperti Model A.
- **STOCK (jual stok jadi)** — produk FINISHED_GOODS berstok tanpa resep ACTIVE; saat PAID
  sistem **memotong stok produk itu sendiri** via FEFO (movement `SALE`), tanpa backflush bahan.

Modul ini sumber pendapatan penjualan dan titik integrasi ke Inventory (pengurangan stok)
serta — di masa depan — ke Finance (penerimaan kas).

**Target pengguna:** Kasir (KASIR), Supervisor Outlet (SUPERVISOR_OUTLET), Owner (OWNER).

### 1.2 In Scope (MVP Sprint 5)
- Shift kasir: open (opening cash), close (expected/actual/discrepancy), satu shift OPEN aktif per kasir/outlet.
- Checkout cart → SalesOrder dengan item + topping (modifier) + qty.
- **Dua mode jual per produk** (MADE_TO_ORDER / STOCK), ditentukan deterministik dari data (§3).
- Pembayaran: skema multi-payment (1 order → banyak payment); **UI MVP satu metode** (OQ-7).
- **Pengurangan stok FEFO saat PAID (atomik, movement `SALE`)**: untuk MADE_TO_ORDER = backflush
  bahan (adonan + topping terpilih); untuk STOCK = potong stok finished-goods produk itu sendiri.
- Diskon manual per-item dan/atau per-order; pajak default 0.
- Topping = modifier yang menempel pada item jual, tiap topping adalah Product ber-stok;
  topping **hanya untuk mode MADE_TO_ORDER** (§3.4).
- Void (sebelum bayar) & **Full-order Refund** (sesudah bayar, OQ-4) dengan pengembalian stok via
  movement baru `SALE_RETURN` (INBOUND, OQ-5).
- Snapshot harga, nama produk, nama topping, dan batch yang dikonsumsi untuk audit & refund.
- Numbering `INV-YYYYMMDD-XXXXXX`, audit fields, company-scope, soft-delete header.
- Reporting dasar (ringkasan penjualan harian, discrepancy shift) — read-only.

### 1.3 Out of Scope (ditunda / future)
- **Promo / bundling engine** (buy-2-get-1, tiered discount, voucher) — ditunda (keputusan User #4).
- **Loyalty / customer points** — future (doc 29 §16).
- **Digital receipt** (email/WhatsApp) — future.
- **Master customer** — tidak ada; nama customer opsional free-text (keputusan #9).
- **PPN / pajak berjenjang** — MVP pajak 0; tak wajib (keputusan #6).
- **Granular permission** `sales.void` / `sales.refund.approve` — follow-up; MVP pakai `sales.manage` (keputusan #7).
- **Posting ke Finance ledger** (cash receipt) — di luar Sprint 5; integrasi menyusul saat modul Finance runtime siap.
- **Status DRAFT ("parkir order")** — SKIP di MVP; follow-up eksplisit (OQ-1, §14).
- **Partial refund** (per item/qty) — MVP full-order saja; follow-up (OQ-4, §14).
- **Guard `pos.*`** granular untuk layar POS — follow-up; MVP layar POS pakai `sales.manage` (OQ-6).

## 3. Dua Mode Penjualan (Made-to-Order + Stock) — penjelasan gamblang

### 3.0 Penentuan mode — DETERMINISTIK dari data, tanpa field baru
Mode penjualan sebuah produk **tidak** disimpan di kolom baru; ditentukan dari data existing
saat checkout:

```
Produk punya resep ACTIVE?
  ├─ YA  → mode MADE_TO_ORDER  (backflush bahan via FEFO)
  └─ TIDAK → produk FINISHED_GOODS dengan stok?
              ├─ YA  → mode STOCK (potong stok produk sendiri via FEFO)
              └─ TIDAK → checkout ditolak (RECIPE.NO_ACTIVE_RECIPE jika bukan FINISHED_GOODS;
                         INVENTORY.INSUFFICIENT_STOCK jika FINISHED_GOODS tapi tanpa stok)
```

Konsekuensi penting:
- Produk **STOCK wajib punya batch stok sendiri** (FINISHED_GOODS); contoh User: air mineral,
  waffle original tanpa topping. Stoknya masuk lewat Goods Receipt / Production Result / Adjustment.
- Produk **MADE_TO_ORDER tidak menyimpan finished-goods**; yang dilacak = bahan (RAW_MATERIAL /
  SEMI_FINISHED) yang dipotong lewat resep.
- Satu produk tidak bisa dua mode sekaligus: keberadaan resep ACTIVE mengunci ke MADE_TO_ORDER.
  Jika produk FINISHED_GOODS kebetulan diberi resep ACTIVE, ia diperlakukan MADE_TO_ORDER
  (backflush), bukan potong stok sendiri.

`SalesOrderItem` menyimpan snapshot mode yang dipakai (`sale_mode`) agar backflush & refund
reproducible meski data master berubah kemudian (lihat §4.4).

### 3.1 Objek yang terlibat
- **Produk Jual (sellable product)**: Product yang muncul di grid POS (mis. "Waffle Original",
  "Air Mineral 600ml").
- **Resep (Recipe/BOM)** — hanya untuk MADE_TO_ORDER: resep ACTIVE milik produk jual, berisi
  `yieldQty` + daftar `recipe_items` (`ingredientProductId`, `qty` base per batch, `uomId`,
  `lossPercentage`). Satu produk hanya boleh punya **satu resep ACTIVE** (dijamin `recipeStatus.ts`
  + index DB).
- **Topping / Modifier** — hanya untuk MADE_TO_ORDER: Product RAW_MATERIAL/SEMI_FINISHED ber-stok.
  Memilih topping = menambah konsumsi bahan topping + (opsional) harga tambahan ke item.
- **Stok finished-goods** — hanya untuk STOCK: batch milik produk jual itu sendiri yang dipotong
  langsung via FEFO.

### 3.2 Mode MADE_TO_ORDER — rumus konsumsi bahan (REUSE `productionConsumption.ts`)
Identik dengan backflushing Production. Untuk setiap item cart `(sellableProductId, qty)`:

```
scaleFactor = qty / recipe.yieldQty
consumedQty(ingredient) = ingredient.baseQty × scaleFactor      // per baris resep
```

- **lossPercentage TIDAK mengurangi stok** — estimasi/planning saja (konsisten dengan keputusan
  Production yang sudah ada; lihat komentar di `productionConsumption.ts`). Konsumsi riil
  memaksimalkan output dari stok tersedia.
- Topping menambah baris konsumsi di luar resep: untuk tiap topping terpilih pada item,
  `consumedQty(topping) = topping.default_qty_per_item × item.qty` (OQ-2; lihat §3.5).

Fungsi `scaledIngredientConsumption(baseQty, scaleFactor)` dan `ingredientRequirementPerUnit`
WAJIB dipakai ulang agar angka preview = angka eksekusi. Dilarang menduplikasi rumus.

### 3.3 Mode STOCK — potong stok finished-goods sendiri
Untuk item cart `(sellableProductId, qty)` dengan mode STOCK:

```
consumedQty(product_id = sellableProductId) = item.qty      // dalam UOM master produk jual
```

- Potong langsung batch milik produk jual via **FEFO** (nearest expiry, non-expired, ACTIVE, qty>0),
  movement `SALE`, atomik SERIALIZABLE — mekanik FEFO identik dengan MADE_TO_ORDER, bedanya
  `product_id` yang dipotong = produk jual itu sendiri, bukan bahan resep.
- **Tidak ada backflush bahan** dan **tidak ada topping** (§3.4). Snapshot batch tetap dicatat di
  `SalesConsumption` untuk refund & audit.
- Jika stok produk jual kurang → `INVENTORY.INSUFFICIENT_STOCK` (rollback seluruh pembayaran).

### 3.4 Topping hanya untuk MADE_TO_ORDER
Topping (modifier) hanya relevan untuk mode MADE_TO_ORDER (produk yang punya resep ACTIVE dan
baris `product_topping`). **Produk mode STOCK dijual apa adanya** — tanpa topping. Jika cart
mengirim topping untuk produk STOCK → ditolak (`TOPPING.NOT_ALLOWED`).

### 3.5 Takaran topping default (OQ-2 — `product_topping.default_qty_per_item`)
Takaran konsumsi per topping per produk disimpan di `product_topping.default_qty_per_item`,
**dalam UOM master produk topping** (mis. gram untuk Selai yang ber-UOM gram, ml untuk Susu
kental manis yang ber-UOM ml). Nilai berikut adalah **rekomendasi default saat setup** dan
**dapat diubah** mengikuti resep asli outlet:

| Topping | Default `default_qty_per_item` | Satuan (mengikuti UOM master topping) |
|---------|-------------------------------|----------------------------------------|
| Selai | 25 | g |
| Meses / ceres | 20 | g |
| Susu kental manis | 25 | ml |
| Choco chips | 15 | g |
| Keju parut | 20 | g |
| Butter / margarin | 10 | g |

Catatan: angka ini hanya nilai default yang bisa disesuaikan per produk per topping di baris join
`product_topping`. Satuan selalu mengikuti UOM master produk topping (bukan UOM baru).

### 3.6 Contoh
**Contoh A (MADE_TO_ORDER) — Waffle + Selai + Meses.**
Resep "Waffle Original": `yieldQty = 10`, item = {Adonan Waffle 1000 g}.
Cart: 2× Waffle Original + topping [Selai (25 g), Meses (20 g)].
- scaleFactor = 2 / 10 = 0.2 → konsumsi Adonan = 1000 × 0.2 = 200 g (movement `SALE`).
- Topping Selai: 25 × 2 = 50 g `SALE`; Meses: 20 × 2 = 40 g `SALE`.
- Harga item = snapshot `sellingPrice` Waffle + harga tambahan Selai + Meses, × qty 2, − diskon item.

**Contoh B (STOCK) — Air Mineral.**
"Air Mineral 600ml" = FINISHED_GOODS, tanpa resep ACTIVE, punya batch stok.
Cart: 3× Air Mineral.
- Mode STOCK → potong 3 unit dari batch Air Mineral via FEFO (movement `SALE`), tanpa backflush.
- Harga item = snapshot `sellingPrice` × 3 − diskon item. Topping tidak diizinkan.

## 4. Definisi Entity & Relasi (konseptual, bukan DDL final)

### 4.1 Diagram relasi
```
Shift (1) ───< SalesOrder (N)
SalesOrder (1) ───< SalesOrderItem (N)
SalesOrderItem (1) ───< SalesOrderItemTopping (N)   // modifier terpilih per item
SalesOrder (1) ───< SalesPayment (N)                // multi-payment
SalesOrder (1) ───< SalesConsumption (N)            // snapshot batch yang dikonsumsi (SALE)
SalesOrder (1) ───< SalesReturn (0..N)              // refund/retur
SalesReturn (1) ───< SalesReturnItem (N)
```
Semua tabel company-scoped (`company_id`) + outlet-scoped (`outlet_id`) sesuai pola tenant doc 35 §3.1.

### 4.2 Shift
Field inti: `id`, `company_id`, `outlet_id`, `shift_number` (opsional), `cashier_user_id`,
`opened_at`, `closed_at`, `opening_cash`, `expected_cash`, `actual_cash` (input manual),
`discrepancy` (= actual − expected), `status` (OPEN/CLOSED), `notes`, + audit fields (§8).
- **`expected_cash` scope (OQ-8):** dihitung saat close = `opening_cash + Σ(payment CASH)
  − Σ(refund CASH)`. **Hanya pembayaran bermetode CASH** yang masuk; CARD / QRIS / BANK_TRANSFER
  TIDAK masuk rekonsiliasi laci (karena tidak menambah kas fisik di laci). Pembayaran non-cash
  tetap tercatat di SalesPayment untuk pelaporan, tapi tidak memengaruhi `expected_cash`.
- Invariant: **maksimal satu Shift OPEN per (cashier_user_id, outlet_id)** — partial unique index `WHERE status='OPEN'`.

### 4.3 SalesOrder (header)
`id`, `company_id`, `outlet_id`, `shift_id`, `invoice_number` (INV-YYYYMMDD-XXXXXX),
`customer_name` (nullable, free-text), `order_date`, `status` (lihat §5),
`item_count`, `subtotal`, `order_discount`, `tax` (default 0), `grand_total`,
`cashier_user_id`, `paid_at`, soft-delete (`deleted_at`), + audit fields.
- `grand_total = subtotal − order_discount + tax`. `subtotal` = Σ item line total (sudah termasuk topping berharga & diskon item).

### 4.4 SalesOrderItem
`id`, `sales_order_id`, `product_id` (produk jual), `sale_mode` (**snapshot** mode saat checkout:
`MADE_TO_ORDER` / `STOCK`, demi reproducibility backflush & refund),
`recipe_id` (**nullable** — snapshot resep ACTIVE yang dipakai; diisi hanya untuk MADE_TO_ORDER,
NULL untuk STOCK), `product_name_snapshot`, `unit_price_snapshot` (dari `products.sellingPrice`),
`qty`, `item_discount`, `toppings_price` (Σ harga topping; 0 untuk STOCK),
`line_total` (= (unit_price + toppings_price) × qty − item_discount).
> `sale_mode` + `recipe_id` di-snapshot agar eksekusi backflush/potong-stok dan refund tetap
> konsisten walau master (resep/tipe produk) berubah setelah transaksi.

### 4.5 SalesOrderItemTopping (modifier terpilih)
`id`, `sales_order_item_id`, `topping_product_id`, `topping_name_snapshot`,
`qty_per_item` (default 1), `extra_price_snapshot` (harga tambahan topping, boleh 0).
> Ini mewujudkan keputusan #2: topping menempel pada item, bukan baris cart terpisah.

### 4.6 SalesPayment
`id`, `sales_order_id`, `payment_method` (CASH / CARD / QRIS / BANK_TRANSFER), `amount`,
`reference_no` (nullable), `paid_at`, + audit. Σ amount harus = `grand_total` (doc 29 §7).

### 4.7 SalesConsumption (snapshot backflush — penting untuk refund & audit)
`id`, `sales_order_id`, `sales_order_item_id`, `product_id` (bahan/topping yang dikonsumsi),
`batch_id`, `qty_consumed`, `movement_id` (ref ke `inventory_movements`).
> Menyimpan **batch mana** yang dipotong per item. Dipakai saat refund untuk mengembalikan ke
> batch asal (lihat §7) dan untuk reconciliation.

### 4.8 SalesReturn / SalesReturnItem
`SalesReturn`: `id`, `company_id`, `outlet_id`, `sales_order_id`, `return_number` (opsional),
`reason`, `refund_amount`, `status` (COMPLETED), `returned_by`, + audit.
`SalesReturnItem`: `id`, `sales_return_id`, `sales_order_item_id`, `qty_returned`,
`refund_line_amount`. Keterkaitan ke batch pengembalian lewat movement `RETURN` + SalesConsumption asal.

## 5. Mekanisme Topping / Modifier — opsi, trade-off, rekomendasi

Perlu cara menautkan "daftar topping yang boleh" untuk sebuah produk jual.

### Opsi A — Modifier Group (fully generic)
Tabel `modifier_group`, `modifier_group_option`, join `product_modifier_group`. Mendukung
min/max pilihan, kelompok ("Pilih saus", "Pilih topping"), required/optional.
- **Pro:** paling fleksibel, standar industri POS.
- **Kontra:** paling banyak tabel + UI config; over-engineering untuk MVP; menyalahi prinsip
  "hindari over-engineering" doc 24 §A.

### Opsi B — Topping tersedia per Kategori produk
Daftar topping ditentukan oleh kategori produk jual (semua "Waffle" berbagi set topping).
- **Pro:** sedikit tabel (`category_topping`).
- **Kontra:** kaku — produk dalam satu kategori dipaksa punya topping sama; sulit untuk
  pengecualian; kategori bukan konsep topping sehingga mencampur tanggung jawab.

### Opsi C — Allowed topping list per produk (REKOMENDASI) ✅
Satu tabel join sederhana `product_topping` (`product_id`, `topping_product_id`,
`default_qty_per_item` default 1, `extra_price` default 0, `sort_order`, `is_active`).
Produk jual menautkan Product-topping yang boleh dipilih di POS; harga tambahan + takaran
per topping disimpan di baris join (bisa beda per produk).
- **Pro:** paling sederhana & konsisten arsitektur (pola join master seperti user-outlet,
  role-permission). Topping tetap Product ber-stok (keputusan #3). Harga/takaran per-produk.
  Mudah di-reuse untuk preview konsumsi.
- **Kontra:** tanpa konsep "group/min-max"; semua topping bersifat opsional. Untuk MVP ini
  justru pas (promo & aturan kompleks ditunda).
- **Jalur upgrade:** bila kelak butuh grouping/required, Opsi A bisa ditambahkan sebagai
  superset tanpa membuang `product_topping` (bisa jadi default group).

**Rekomendasi:** **Opsi C**. Mewujudkan keputusan #2 & #3, minim tabel, konsisten pola join
master yang sudah ada, dan menyisakan jalur ke Opsi A sebagai future extension.

## 6. Status Lifecycle & State Machine

### 6.1 SalesOrder (MVP — DRAFT di-skip, OQ-1)
```
PENDING_PAYMENT ──pay(sukses + potong stok FEFO)──> PAID ──refund(full)──> REFUNDED
PENDING_PAYMENT ──void/cancel──> CANCELLED
```
Diizinkan: `PENDING_PAYMENT→PAID`, `PENDING_PAYMENT→CANCELLED`, `PAID→REFUNDED`.
Dilarang: `REFUNDED→PAID`, `CANCELLED→*`, `PAID→CANCELLED` (gunakan REFUNDED).

> **Catatan desain (OQ-1):** status `DRAFT` ("parkir order") **di-skip di MVP** — submit cart
> langsung membuat order `PENDING_PAYMENT`. DRAFT/parkir order dicatat sebagai **follow-up**
> (§14). Bila kelak diaktifkan, transisi `DRAFT→PENDING_PAYMENT` dan `DRAFT→CANCELLED` ditambahkan
> tanpa mengubah aturan posting stok.
> **Stok hanya dipotong pada transisi `PENDING_PAYMENT→PAID`** (bukan saat checkout).

### 6.2 Shift
```
OPEN ──close(rekonsiliasi)──> CLOSED
```
Diizinkan: `OPEN→CLOSED`. Dilarang: `CLOSED→OPEN`, transaksi pada shift CLOSED.

## 7. Checkout → Pay → Potong Stok FEFO (dua mode, alur transaksi atomik)

### 7.1 Checkout (buat SalesOrder PENDING_PAYMENT)
1. Validasi shift kasir OPEN (keputusan #10) → else `SHIFT.NOT_OPEN`.
2. **Resolusi mode per item cart (deterministik, §3.0):**
   - Produk punya resep ACTIVE → `sale_mode = MADE_TO_ORDER`, snapshot `recipe_id`.
   - Tidak ada resep ACTIVE & produk `FINISHED_GOODS` → `sale_mode = STOCK`, `recipe_id = NULL`.
   - Tidak ada resep ACTIVE & bukan `FINISHED_GOODS` → tolak baris itu `RECIPE.NO_ACTIVE_RECIPE`.
3. **Validasi topping bergantung mode:**
   - MADE_TO_ORDER: tiap topping harus ada di `product_topping` produk & aktif → else `TOPPING.NOT_ALLOWED`.
   - STOCK: topping tidak diizinkan; jika ada topping dikirim → `TOPPING.NOT_ALLOWED`.
4. Snapshot harga: `unit_price` dari `products.sellingPrice`, `extra_price` topping dari join (anti-tamper #5).
5. Hitung `subtotal`, diskon (item & order; diskon ≤ total, doc 29 §7), `tax=0`, `grand_total`.
6. Generate `invoice_number` INV-YYYYMMDD-XXXXXX (counter per company+hari, pola seperti `_generateNumber` Production).
7. Persist header + items (+ `sale_mode`) + toppings, status `PENDING_PAYMENT`. **Belum menyentuh stok.**
   > Catatan: validasi ketersediaan stok untuk mode STOCK dilakukan final & authoritative saat
   > PAID (§7.2) di bawah lock FEFO; checkout tidak menjamin stok masih ada saat bayar.

### 7.2 Pay + Potong Stok (transisi PENDING_PAYMENT → PAID) — ATOMIK
Dalam **satu transaksi `BEGIN` + `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE`** (reuse pola
`ProductionOrderRepositoryPostgres.createInstant` & `InventoryRepositoryPostgres.postMovements`):

1. Lock & re-baca SalesOrder; pastikan status `PENDING_PAYMENT` (idempotency guard — jika sudah
   `PAID`, tolak/no-op → `SALES_ORDER.ALREADY_PAID`).
2. Validasi Σ payment == `grand_total` (doc 29 §7) → else `PAYMENT.AMOUNT_MISMATCH`.
3. Untuk tiap item → bangun daftar konsumsi stok **sesuai `sale_mode`**:
   - **MADE_TO_ORDER:** dari resep `requiredQty(ingredient) = scaledIngredientConsumption(baseQty,
     qty/yieldQty)` per baris + dari topping `default_qty_per_item × item.qty` per topping.
     Target potong = batch **bahan/topping**.
   - **STOCK:** satu baris konsumsi `product_id = produk jual`, `requiredQty = item.qty`.
     Target potong = batch **produk jual itu sendiri**. Tanpa topping.
4. Untuk tiap target potong: **FEFO pick di bawah `FOR UPDATE`** (nearest expiry, non-expired
   `>= bizDate`, status ACTIVE, qty>0) — query identik dengan backflush Production.
5. Update `inventory_batches.qty_available` + set `CONSUMED` saat 0; append `inventory_movements`
   `movement_type='SALE'` dengan **source keys**: `source_document_type='SALES_ORDER'`,
   `source_document_id=orderId`, `source_document_item_id=salesOrderItemId`,
   `source_document_allocation_id=batchId` (doc 35 §8; idempotency source-key kini termasuk
   `movement_type`, migrasi 049). Berlaku untuk kedua mode (yang berbeda hanya `product_id` batch
   yang dipotong).
6. Insert `SalesConsumption` (snapshot batch + movement_id) per potongan (kedua mode).
7. Bila stok tak cukup di salah satu baris → **ROLLBACK seluruh pembayaran** (larangan stok
   negatif #11) → `INVENTORY.INSUFFICIENT_STOCK` (berlaku untuk bahan MADE_TO_ORDER maupun
   finished-goods STOCK). Order tetap `PENDING_PAYMENT`.
8. Insert `SalesPayment`(s). Set header `status='PAID'`, `paid_at=NOW()`.
9. COMMIT. Fire event `SalesOrderPaid` (receipt).

**Concurrency:** SERIALIZABLE + `FOR UPDATE` pada batch mencegah lost-update/oversell saat dua
kasir menjual bahan yang sama (konsisten inventory rule #6). Konflik serialisasi → retry/transient error.

**Idempotency:** guard status (#1 di atas) + unique source-key (`SALES_ORDER`+item+batch+`SALE`)
mencegah double-posting bila request diulang.

## 8. Sales Return / Refund

### 8.1 Prinsip (OQ-4: full-order; OQ-5: movement `SALE_RETURN`)
Refund MVP adalah **full-order** (seluruh order di-refund; partial = future, §14). Refund
mengembalikan **seluruh stok** yang sebelumnya dikonsumsi (bahan untuk MADE_TO_ORDER; finished-goods
untuk STOCK) ke **batch asal** yang dicatat di `SalesConsumption` (traceability akurat), mengikuti
pola doc 35 §8 "reversal harus derive dari posted movement".

**Movement = `SALE_RETURN` (INBOUND) — movement type BARU (OQ-5).** `RETURN` existing tergolong
OUTBOUND di `movementTypes.ts`, sehingga tidak cocok untuk menambah stok kembali. Implementasi
(Fase 3, **bukan di dokumen ini**) perlu:
- **(a)** menambah `'SALE_RETURN'` ke whitelist `MOVEMENT_TYPES` (migrasi: perbarui constraint
  `movement_type`) **dan** mengklasifikasikannya sebagai **INBOUND** di
  `INBOUND_MOVEMENT_TYPES` (`movementTypes.ts`);
- **(b)** source keys refund: `source_document_type='SALES_RETURN'`, `source_document_id=salesReturnId`,
  `source_document_item_id=salesReturnItemId`, `source_document_allocation_id=batchId` (doc 35 §8).

### 8.2 Alur (atomik, SERIALIZABLE)
1. Validasi order `PAID` & permission (`sales.manage`, keputusan #7).
2. Full-order refund: ambil **semua** `SalesConsumption` milik order.
3. Untuk tiap konsumsi: kembalikan `qty_consumed` penuh ke `batch_id` asal (reaktivasi batch bila
   `CONSUMED`), append movement `SALE_RETURN` (INBOUND) dengan source keys
   `source_document_type='SALES_RETURN'` (§8.1). Pengembalian derive dari posted movement `SALE`,
   bukan hanya snapshot item.
4. Insert `SalesReturn` + `SalesReturnItem`, hitung `refund_amount = grand_total` (full-order).
5. Set order `status='REFUNDED'`.
6. COMMIT. Fire `SalesOrderRefunded`.

> **Catatan rekonsiliasi kas (OQ-8):** refund bermetode CASH mengurangi `expected_cash` shift
> (§4.2); refund non-cash tidak memengaruhi laci.

### 8.3 Otorisasi
MVP: `sales.manage`. Granular `sales.refund.approve` = follow-up (doc 29 §11 vs seed aktual, lihat §9).

## 10. API Surface (usulan + guard)

Selaras doc 29 §13, diselaraskan ke permission aktual. Base `/api/v1`. Semua tenant-aware
(company context + outlet scope, doc 35 §3.1).

| Method & Path | Guard | Keterangan |
|---------------|-------|-----------|
| `POST /sales/shifts/open` | `shift.manage` | Buka shift (opening cash) |
| `POST /sales/shifts/:id/close` | `shift.manage` | Tutup shift + rekonsiliasi |
| `GET /sales/shifts` / `:id` | `shift.read` | List/detail shift |
| `GET /sales/pos/products` | `sales.manage` (OQ-6) | Grid produk jual + mode (MADE_TO_ORDER/STOCK) + topping tersedia (per outlet) |
| `POST /sales/orders` | `sales.manage` | Checkout → buat order PENDING_PAYMENT |
| `POST /sales/orders/:id/pay` | `sales.manage` | Bayar + potong stok FEFO dua mode (atomik) |
| `POST /sales/orders/:id/void` | `sales.manage` | Void order belum dibayar → CANCELLED |
| `POST /sales/orders/:id/returns` | `sales.manage` | Refund/retur (reversal stok) |
| `GET /sales/orders` / `:id` | `sales.read` | List/detail sales order |

Response & error mengikuti standar `{ success, data, meta }` / `{ success, message, errors }`
(doc 20 §5). Error code konsisten:
- `SHIFT.NOT_OPEN` — tidak ada shift OPEN saat transaksi.
- `RECIPE.NO_ACTIVE_RECIPE` — produk tanpa resep ACTIVE **dan bukan** FINISHED_GOODS berstok
  (tidak memenuhi syarat mode mana pun).
- `INVENTORY.INSUFFICIENT_STOCK` — stok kurang: bahan/topping (MADE_TO_ORDER) atau finished-goods
  (STOCK, termasuk produk STOCK yang tak punya batch stok).
- `TOPPING.NOT_ALLOWED` — topping tidak terdaftar di `product_topping`, atau topping dikirim untuk
  produk mode STOCK.
- `PAYMENT.AMOUNT_MISMATCH` — Σ payment ≠ `grand_total`.
- `SALES_ORDER.ALREADY_PAID` — order sudah PAID (idempotency guard).
